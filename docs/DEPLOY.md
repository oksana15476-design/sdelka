# Развёртывание: образ и подъём одной командой

Статус: **[установлено]** — выполнено на живом демоне Docker: сборка обоих
образов, подъём стека с нуля (`docker compose up -d`, 7,5 с до готовности),
накат миграций до версии `0023`, обращение к `/health` во всех четырёх
состояниях. Приведённые ответы — фактический вывод, а не пример.

**[установлено]** — в сети, перехватывающей TLS, холодная сборка падает на
`SELF_SIGNED_CERT_IN_CHAIN`, и обходится это передачей корневого сертификата
(§3, второй вариант); именно так собирались образы здесь. На тёплом кэше
`docker compose build` проходит и без него.

Документ рассчитан на человека, который видит проект впервые. Порядок шагов
менять нельзя: он и есть содержание документа.

---

## 0. Что нужно на машине

- Docker с BuildKit (`docker build` версии 23+) и `docker compose` v2;
- ничего больше. Ни node, ни pnpm, ни Postgres: всё внутри образов.

Проверка: `docker version` и `docker compose version` отвечают.

---

## 1. Что тут из чего состоит

| Что | Где описано | Что делает |
| --- | --- | --- |
| Образ приложения | `Dockerfile`, ступень `runtime` | процесс интерфейса (Next, `apps/web`) |
| Образ наката | `Dockerfile`, ступень `migrator` | применяет миграции `packages/db`, отрабатывает и завершается |
| Стек | `compose.yaml` | Postgres + накат + приложение, в этом порядке |
| Роли кластера | `docker/postgres-init.sh` | заводит роли один раз, при создании тома |
| Проверка здоровья | `apps/web/src/app/health/route.ts` | `GET /health` |

Два образа, а не один, — потому что **накат миграций отдельный шаг**.
Приложение, которое мигрирует базу само на старте, при двух копиях делает это
дважды и идёт в базу правами, которых у него быть не должно (инвариант 21:
роль приложения не имеет прав на изменение схемы и журнала аудита).

## 2. Переменные окружения

Полный перечень с объяснением каждой — в `.env.example` (значений там нет и не
будет, красная линия №12). Для подъёма стека нужна **одна**:

| Переменная | Обязательна | Что это |
| --- | --- | --- |
| `SDELKA_DB_PASSWORD` | да, для стека | пароль логин-роли Postgres. Из него же собирается строка подключения |

Пароль обязан быть безопасным для URL — он подставляется в
`postgresql://sdelka:<пароль>@db:5432/sdelka`. Символы `@ : / ? # %` в нём
недопустимы. Готовый генератор:

```sh
export SDELKA_DB_PASSWORD=$(head -c 18 /dev/urandom | base64 | tr -d '/+=')
```

Пароль не коммитится, не пишется в файл в репозитории и не пересылается в
переписке. Держите его в менеджере паролей или в хранилище секретов стенда.

Приложение и накат читают `SDELKA_DATABASE_URL`. В стеке её **собирает
`compose.yaml`** из пароля выше — задавать её руками не нужно. Она нужна
руками только при запуске образа без стека (§7).

## 3. Подъём одной командой

```sh
export SDELKA_DB_PASSWORD=$(head -c 18 /dev/urandom | base64 | tr -d '/+=')
docker compose up -d --build
```

Всё. Compose соберёт оба образа, поднимет Postgres, дождётся его готовности,
прогонит накат, дождётся его **успешного завершения** и только потом запустит
приложение.

Если ваша сеть перехватывает TLS (корпоративный прокси, песочница сборщика) и
сборка падает на `SELF_SIGNED_CERT_IN_CHAIN`, соберите образы отдельной
командой, передав корневой сертификат вашей сети, и поднимайте стек без
`--build`:

```sh
docker build --secret id=ca_bundle,src=/путь/к/ca-bundle.crt -t sdelka-web:local .
docker build --secret id=ca_bundle,src=/путь/к/ca-bundle.crt --target migrator -t sdelka-migrate:local .
docker compose up -d
```

Сертификат виден только той команде сборки, которая его читает, и **не остаётся
ни в одном слое образа**.

## 4. Накат миграций отдельным шагом

Стек накатывает миграции сам — службой `migrate`, до запуска приложения.
Запустить накат руками (например, после обновления образа):

```sh
docker compose run --rm migrate
```

Повтор на уже накаченной базе — **штатный успех**, а не ошибка:
`applied=-`, код выхода 0. Команда, падающая на повторе, приучает игнорировать
её код выхода.

С машины разработчика, без контейнеров, тот же накат — той же командой проекта:

```sh
pnpm db:migrate            # это и есть packages/db/src/cli/migrate.ts
```

Образ наката запускает ровно этот файл. Второго раннера миграций в проекте нет.

## 5. Как проверить, что поднялось

```sh
docker compose ps
curl -fsS http://127.0.0.1:3000/health
```

Проверка здоровья отвечает `200` **только если** процесс жив, база доступна и
схема накачена:

```json
{"status":"ok","db":"ready","schema":"0023"}
```

Ответ `503` и род отказа — если что-то из этого не так:

| Тело ответа | Что случилось | Что делать |
| --- | --- | --- |
| `{"status":"fail","db":"unreachable"}` | до базы не добрались | `docker compose ps db`, `docker compose logs db` |
| `{"status":"fail","db":"unmigrated"}` | база пустая, накат не прошёл | `docker compose run --rm migrate` |
| `{"status":"fail","db":"unconfigured"}` | нет строки подключения | см. §2 |
| `{"status":"fail","db":"error","code":"28P01"}` | база ответила отказом (здесь: неверный пароль) | сверьте `SDELKA_DB_PASSWORD` с тем, с каким создавался том (§6) |

«Процесс запустился» проверкой здоровья не считается: контейнер без базы
отвечает на порт и выглядит здоровым до первой денежной операции.

Ту же пробу выполняет сам Docker (`HEALTHCHECK` в `Dockerfile`):

```sh
docker inspect --format '{{.State.Health.Status}}' sdelka-web-1
```

Учтите: `healthy` → `unhealthy` переключается после **трёх** подряд неудачных
проб с интервалом 30 с, то есть примерно через полторы минуты. Мгновенный ответ
— у `curl`, а не у этого поля.

## 6. Как откатиться

**Откатить приложение** (база остаётся как есть):

```sh
docker compose up -d --no-deps web        # с предыдущим образом sdelka-web:local
```

Приложение старой сборки на новой схеме — состояние, которое проект считает
недопустимым: старый код не знает, что изменила чужая миграция. Сверьте:

```sh
docker compose run --rm --entrypoint sh migrate -c \
  'node --experimental-strip-types packages/db/src/cli/schema-check.ts'
```

`db.schema.ahead` означает, что база впереди кода — откатывать надо не
приложение, а решение об откате: обратных миграций в проекте нет намеренно.

**Погасить стек, сохранив данные:**

```sh
docker compose down
```

**Погасить и стереть базу целиком** (том с данными, все сделки, весь журнал
аудита — безвозвратно):

```sh
docker compose down -v
```

Это же единственный способ пересоздать роли кластера: `docker/postgres-init.sh`
выполняется **только при первом создании тома**. Сменили `SDELKA_DB_PASSWORD`
при существующем томе — пароль роли в базе останется прежним, и приложение
получит `28P01`. Либо смените пароль в самой базе:

```sh
docker compose exec db psql -U postgres -d sdelka \
  -c "ALTER ROLE sdelka PASSWORD 'новый'"
```

— либо стирайте том и поднимайтесь заново.

## 7. Запуск образа без стека

```sh
docker run --rm -p 3000:3000 \
  -e SDELKA_DATABASE_URL='postgresql://пользователь:пароль@хост:5432/база' \
  sdelka-web:local
```

Порт меняется переменной: `-e PORT=8080 -p 8080:8080`.

**Ворота старта.** Контейнер, которому не хватает обязательной переменной,
падает сразу, кодом 1, и называет её:

```
$ docker run --rm sdelka-web:local
config.env.incomplete scope=app count=1 reference=.env.example
SDELKA_DATABASE_URL config.env.absent read_by=packages/db/src/env.ts,...
```

Это тот же механизм, что `pnpm env:check`, а не второй: в образ едет исходник
`packages/config`, и перечень переменных у проекта один
(`packages/config/src/registry.ts`).

## 8. Чего этот стек не делает

Названо честно, чтобы не приняли за готовый прод:

- **[установлено]** суперпользователь кластера и логин-роль приложения делят
  один пароль. Для локального подъёма это осознанное упрощение; в проде база
  живёт отдельно, роли заводит её владелец, и пароли разные;
- **[установлено]** порт Postgres наружу не публикуется; доступ — только через
  `docker compose exec db psql -U postgres -d sdelka`;
- **[установлено]** резервных копий стек не снимает. Копии и проверенное
  восстановление — `packages/backup`, отдельный процесс;
- **[открыто]** боевое развёртывание (оркестратор, несколько копий приложения,
  раскатка без простоя, хранение секретов) не описано и не проверялось. Пока
  этого нет, `compose.yaml` — стенд, а не прод.

## 9. Что внутри образов (и чего внутри нет)

Образ приложения (`runtime`, ~70 МБ содержимого в `/app`):

- вывод `standalone` Next, клиентская сборка, статика и шрифты;
- исходник `packages/config` под ворота старта;
- **нет** pnpm, devDependencies, тестов, исходников интерфейса, инструментов
  сборки, сборочного корневого сертификата и ни одного значения секрета.

Образ наката (`migrator`, ~4,6 МБ содержимого в `/repo`):

- исходники `packages/db` и `packages/config`, файлы миграций, драйвер `pg`;
- **нет** ни next, ни react, ни vitest, ни pnpm.

Оба процесса работают от непривилегированного пользователя `sdelka` (uid
10001), а не от root.
