# Экраны и компоненты: кабинет покупателя, кабинет получателя, консоль операций

**Версия:** 0.1 · **Дата:** 2026-08-31 · **Статус:** на приёмку владельцем
**Основание:** `docs/product/PRODUCT.md` 0.2, `docs/product/CABINETS.md` 0.1,
`docs/product/FUNCTIONAL.md` 0.1
**Что это:** спецификация экранов — структура, данные, состояния, поведение,
крайние случаи, адаптивность, компоненты. **Не визуальный стиль.** Дизайн-системы
в проекте пока нет; этот документ — вход для неё и для разработки.

**Чего в документе нет намеренно:**
цвета, шрифты, отступы, иконки, тайминги анимаций — это отдельный проход
(`design-system`, `design-token`, `color-system`, `typography-scale`);
готовые тексты — их пишет связка копирайтер → главред, здесь только ключи и
брифы «что текст должен сообщить»;
бизнес-логика — она в `FUNCTIONAL.md`, здесь только её отражение в интерфейсе.

**Маркеры** (по правилу проекта): **[установлено]** — следует из принятых
документов; **[решение]** — проектное решение этого документа, обратимо;
**[гипотеза]** — требует проверки; **[открыто]** — блокирует, вынесено в §8.

## 0. Как читать документ

### 0.1 Нотация вайрфреймов

Макеты — низкая точность, только структура и приоритет. Условные обозначения:

| Запись | Смысл |
|---|---|
| `«ключ.локализации»` | Текстовый слот. **В макете никогда не стоит готовый текст** — только ключ |
| `{данные: путь}` | Значение из данных, форматируется механизмом локали |
| `[Кнопка «ключ»]` | Основное действие |
| `[[Кнопка «ключ»]]` | Единственное основное действие экрана (не более одного) |
| `[ Кнопка «ключ» ]ᵈ` | Действие в состоянии «недоступно», с обязательной причиной рядом |
| `▸ ключ` | Раскрывающийся блок, свёрнут по умолчанию |
| `▣` | Компонент из инвентаря §6, назван по имени |
| `→ S-XX` | Переход к состоянию с кодом |
| `⚠ ключ` | Блокирующее предупреждение, не сворачивается |
| `⏱` | Слот таймера дедлайна |
| `·····` | Строка данных, повторяемая |

### 0.2 Идентификаторы

- Экраны: `B-*` покупатель, `R-*` получатель, `O-*` консоль операций.
- Состояния экрана: `B-03/S-04`.
- Компоненты: `C-**` (§6).
- Состояния «где деньги»: `M-**` (§2.2).

### 0.3 Контракт экрана — три вопроса

Каждый экран во **всех** состояниях, включая пустое, загрузку и ошибку, отвечает:

1. **Где сейчас деньги** — кто фактически держит сумму прямо сейчас.
2. **Что произойдёт дальше** — следующее событие и когда, включая «что случится,
   если никто ничего не сделает».
3. **Что требуется от меня** — ровно одно действие или явное «ничего, ждём X».

**Правило приёмки:** если на экран нельзя показать пальцем и получить три ответа
за пять секунд — экран не принят. Проверяется по чек-листу §7 на каждом
состоянии, а не только на «нормальном».

Это не лозунг, а причина ряда решений ниже: например, почему у пустого состояния
кабинета всё равно есть строка о местонахождении денег, и почему экран ошибки
загрузки говорит «деньги в безопасности, мы не смогли показать страницу», а не
«что-то пошло не так».

### 0.4 Терминология и запреты в интерфейсе

Запреты — не стилистика, а правовая обязанность (`CLAUDE.md`, красные линии;
`CABINETS.md` §0.1).

| Запрещено | Вместо этого | Почему |
|---|---|---|
| «эскроу», «escrow», «ესქრou» в любом виде | «расчёт по сделке», «резервирование средств» | Эскроу-агент по закону только банк или микробанк |
| «отправить деньги продавцу», «перевести продавцу» | «подтвердить условия расчёта» | Клиент не даёт поручение банку. Поручение даёт платформа |
| «вы перевели», «вы выплатили» | «расчёт исполнен» | То же |
| «ваши деньги у нас», «на нашем счёте» | «на счёте номинального держания в {банк}» | Это не наш баланс, это чужие деньги |
| «мы разблокируем, когда сочтём нужным» | «расчёт исполняется при подтверждённой регистрации» | Условие по воле сторон делает сделку ничтожной |
| «гарантируем», «безотзывно», «заблокировано навсегда» | формулировки через факты и сроки | Безотзывное поручение ничтожно; ложное обещание = потребительский риск |
| «средства заморожены» (о резерве) | «зарезервированы под сделку до ⏱» | Заморозка — санкционный термин, у него другое значение |

Термины, требующие **одного** перевода во всех трёх языках и во всех кабинетах
(глоссарий ведёт главред, ключи — в неймспейсе `glossary.*`): резерв, расчёт,
откат, транш, референс, счёт-источник, номинальное держание, пакет доказательств,
наблюдение, покрытие.

### 0.5 Что финализируется не здесь

Каждый ключ ниже сопровождается **копи-брифом**: что текст обязан сообщить, чего
не имеет права обещать, лимит длины. Финальные формулировки — копирайтер →
главред. Юридически чувствительные слоты помечены **⚖** — они идут через
`legal-compliance-ru`, минуя главреда: карточка подтверждения средств, правила
распределения расходов при срыве, текст о невозвратности спреда, декларация PEP,
формулировка условия расчёта, тексты согласий.

## 1. Сквозные правила

### 1.1 Локализация

**[установлено]** Русский, английский, грузинский с первого дня. Консоль
операций — русский и английский, без грузинского.

**Ни одной строки текста в компонентах.** Компонент принимает ключ или уже
разрешённую строку, но никогда не содержит литерал. Это проверяется линтером на
литералы в JSX, а не ревью **[решение]**.

**Схема ключей.** `<область>.<экран>.<блок>.<элемент>[.<состояние>][.<роль>]`

```
buyer.deal.whereMoney.reserved.title
buyer.deal.whereMoney.reserved.body
buyer.topup.payerRule.warning
payee.assurance.outcomes.registered.body
ops.payout.approve.blocked.samePreparer
common.deadline.consequence.rollback
glossary.tranche
```

Области: `buyer`, `payee`, `ops`, `common`, `glossary`, `legal`, `notify`.
Один ключ — один смысл. **Ключи не переиспользуются между областями**, даже если
русский текст совпадает: в грузинском он может не совпасть.

**Плюрализация** — через ICU MessageFormat, все формы каждого языка (ru: one/few/
many/other, en: one/other, ka: one/other + собственные особенности числительных).
Ни одной конкатенации «{n} + слово».

**Числа, даты, валюты, имена** — через `Intl`, не своими функциями. Лари
форматируется по грузинским правилам. **Суммы приходят с сервера в целых минорных
единицах** и форматируются на клиенте; в компонент никогда не передаётся число с
плавающей точкой (красная линия №4).

**Длина строк.** Макеты проверяются на грузинском и русском, не на английском.

| Тип слота | Бюджет EN | Запас на RU | Запас на KA | Поведение при переполнении |
|---|---|---|---|---|
| Метка кнопки | ≤ 20 симв. | ×1.4 | ×1.6 **[гипотеза]** | Перенос на 2 строки, кнопка растёт. **Никогда не обрезается** |
| Заголовок блока | ≤ 40 | ×1.35 | ×1.5 | Перенос |
| Тело блока | ≤ 240 | ×1.35 | ×1.5 | Растёт |
| Ячейка таблицы (текст) | ≤ 32 | ×1.35 | ×1.5 | Обрезка + тултип + полное значение в детали |
| Ячейка таблицы (деньги, дата, статус) | — | — | — | **Не обрезается никогда.** Колонка расширяется, обрезаются соседние |
| Метка поля формы | ≤ 30 | ×1.4 | ×1.6 | Перенос, поле не сдвигается |
| Чип фильтра | ≤ 18 | ×1.4 | ×1.6 | Перенос списка чипов на новую строку |

Коэффициенты — **[гипотеза]**, уточняются после первого прохода реальных
переводов; до этого макеты проверяются на псевдолокали, растягивающей EN на 60%.

**Правило вёрстки:** никаких фиксированных ширин у элементов с текстом. Кнопки,
чипы, бэджи, табы — по контенту с минимальной шириной. Сетки — на `minmax()`.

**Задел под RTL:** логические свойства (`inline-start/end`, `margin-inline`)
вместо физических с первого коммита. Иконки направления зеркалируются, иконки
объектов — нет. Порядок чисел и денежных сумм в RTL не переворачивается.

**Язык выбирается пользователем, не геолокацией**, хранится в профиле,
применяется ко всем каналам, включая письма. Переключатель языка доступен **до
входа** (на экране входа) — иностранец не должен угадывать пароль на незнакомом
языке. ▣ C-21.

**Имена собственные** (стороны, банки, адреса объектов) не переводятся и
показываются в исходном алфавите; в консоли — с транслитерацией второй строкой,
см. §5.4 и `FUNCTIONAL.md` §5.3.

### 1.2 Часовые пояса и дедлайны

Продукт трансграничный: покупатель в другом часовом поясе, дедлайн привязан к
банковскому дню в Тбилиси. Показ дедлайна «до 18:00» без зоны — прямой путь к
пропуску срока и спору.

**[решение]** Дедлайн всегда показывается **двумя строками**: основная — время
операционной зоны (Asia/Tbilisi) с явной меткой зоны; вторая — то же время в
локальной зоне устройства пользователя, если она отличается. Плюс относительный
остаток («через 4 ч 12 мин») как третий, вспомогательный элемент.
Относительное время **никогда не единственное** представление дедлайна.

Ниже дедлайна — **всегда** последствие: что произойдёт при его наступлении, если
никто ничего не сделает. Без последствия таймер не рендерится (проверяется
типом: `Deadline` требует `consequenceKey`) **[решение]**.

**Пауза часов.** При недоступности реестра часы сделки приостанавливаются и
дедлайны сдвигаются (`FUNCTIONAL.md` §3.5). В интерфейсе это отдельное состояние
таймера: отсчёт остановлен, показана причина, показано «новый срок будет назван
после восстановления» — а не молчаливое изменение цифры. Обе стороны видят
одинаково. ▣ C-03.

### 1.3 Брейкпоинты и устройства

| Класс | Ширина | Кто |
|---|---|---|
| `xs` | 360–479 | Покупатель, основной сценарий |
| `sm` | 480–767 | Покупатель |
| `md` | 768–1023 | Планшет, получатель в дороге |
| `lg` | 1024–1439 | Получатель, консоль — основной |
| `xl` | ≥ 1440 | Консоль, застройщик с реестрами |

- **Кабинет покупателя — mobile-first.** Проектируется от 360 px, десктоп — та же
  вертикальная лента, ограниченная по ширине измерения строки (60–75 симв.),
  без превращения в двухколоночную панель. Одна колонка — не ограничение, а
  решение: сделка читается сверху вниз один раз, а не сканируется.
- **Кабинет получателя — desktop-first**, но карточка подтверждения средств и
  экран реквизитов обязаны полностью работать на `xs`: продавец смотрит
  подтверждение с телефона у нотариуса. Это проверяется отдельно **[решение]**.
- **Консоль — desktop-first**, минимум `lg`. Ниже `md` — экран-заглушка «консоль
  не предназначена для телефона», кроме двух исключений, которые обязаны работать
  на телефоне: **экран утверждения выплаты** и **дежурный дашборд** (руководителя
  вызывают ночью). **[решение]**
- Сенсорные цели ≥ 44×44 CSS px на всех классах, включая консоль на планшете.
- Ни один экран не ломается при зуме 200% и при системном шрифте +30%.

### 1.4 Универсальные состояния экрана

Каждый экран специфицирует **все** применимые состояния. Отсутствие спецификации
состояния — незакрытый экран, а не «потом добавим».

| Код | Состояние | Правило |
|---|---|---|
| `SC-load` | Загрузка | Скелет формы контента, не спиннер по центру. Каркас (навигация, блок безопасности, известные из кэша суммы) виден сразу |
| `SC-ready` | Данные есть | — |
| `SC-empty` | Данных нет законно | Объясняет, почему пусто, и что появится. **Пустой ≠ ошибка** |
| `SC-partial` | Часть данных не пришла | Показываем то, что есть; неудавшийся блок — локальная ошибка с повтором. **Экран целиком не падает из-за одного блока** |
| `SC-stale` | Данные из кэша, обновление не удалось | Метка «данные на {время}», кнопка обновления. Денежные суммы в `stale` **помечаются явно** и действия по ним блокируются |
| `SC-error` | Блокирующая ошибка | Что произошло, деньги в безопасности, что делать, повтор, идентификатор обращения |
| `SC-denied` | Доступ запрещён | Что именно недоступно и почему; кто может дать доступ; никогда не «404» вместо «нет прав», кроме случаев, где сам факт существования сделки — тайна |
| `SC-offline` | Нет сети | Баннер, кэш, очередь действий не создаётся: **денежные действия не ставятся в очередь офлайн** |
| `SC-frozen` | Операции приостановлены (комплаенс/инцидент) | Экран читаем, действия недоступны с причиной и сроком |

**Правило загрузки денег:** сумма никогда не отображается «примерно» и не
анимируется от нуля. Пока сумма не подтверждена сервером — на её месте скелет.
Показать неверную сумму хуже, чем не показать никакой.

**Правило ошибки:** ни на одном экране покупателя и получателя сообщение об
ошибке не остаётся без ответа на вопрос «где мои деньги». Шаблон:
`«common.error.<code>.title»` + `«common.error.moneySafe»` + действие + номер
обращения. ▣ C-14.

### 1.5 Постоянный блок безопасности

**[установлено]** Присутствует во всех кабинетах и во всех письмах.

- Кабинет покупателя: закреплён в подвале каждого экрана + развёрнутый экран B-07.
  На экране пополнения — **не в подвале, а непосредственно над реквизитами**.
- Кабинет получателя: подвал + постоянно на экране реквизитов выплаты.
- Консоль: в виде памятки на экранах, где оператор общается со сторонами.
- Не сворачивается, не скрывается, не является модальным окном, которое можно
  закрыть навсегда.
- Содержит **[установлено]**: мы не сообщаем реквизиты по телефону, почте и в
  мессенджере; единственное место, где вы видите реквизиты — этот кабинет; мы
  никогда не просим перевести деньги на другой счёт.
- Содержит действие «сообщить о подозрительном контакте» → §3.7. ▣ C-05.

### 1.6 Уведомления и почта

**[установлено]** Никаких ссылок на действия в письмах. Письмо говорит «есть
обновление по сделке», ссылка ведёт в кабинет, действие совершается там.

Следствие для экранов: при входе по ссылке из письма пользователь попадает на
экран сделки, а не на действие. Если действие требуется — оно уже видно в блоке 2
как единственное. Глубокие ссылки на подтверждение, изменение реквизитов и вывод
средств **не существуют** — эти экраны недостижимы иначе, чем навигацией внутри
сессии **[решение]**.

### 1.7 Доступность — базовая линия для всех экранов

WCAG 2.1 AA как минимум. Проверяется на каждом экране, а не в конце.

- Один `<h1>` на экран; заголовки без пропусков уровней; ориентиры `header/nav/
  main/aside/footer`.
- Статус денег и статус сделки **не передаются одним цветом**: цвет + текст +
  форма индикатора. Дальтоник обязан различать «зарезервировано» и «возвращено».
- Таймер дедлайна: обновление в `aria-live="polite"` не чаще раза в минуту (иначе
  скринридер зачитывает его непрерывно). За 10 минут до конца — одно объявление
  `assertive`.
- Ограничение по времени (фиксация курса) — WCAG 2.2.1: обязана быть возможность
  продлить или пересчитать; истечение не должно приводить к потере введённых
  данных.
- Все действия доступны с клавиатуры; модальные окна с ловушкой фокуса и
  возвратом фокуса; порядок табуляции соответствует визуальному.
- Ошибки формы связаны с полем (`aria-describedby`), сводка ошибок вверху
  фокусируема и ведёт к полю.
- `prefers-reduced-motion` уважается; мерцание таймера и шиммер скелетов
  отключаются.
- Загрузка документов доступна с клавиатуры; drag-and-drop — только дополнение,
  никогда единственный способ.

## 2. Модель состояний, на которую опираются экраны

### 2.1 Состояния из продуктовых документов

**[установлено]** (`PRODUCT.md` §7):

```
Сделка:  Черновик → Стороны проверены → Объект проверен → Средства заведены
         → Зарезервированы → Подано на регистрацию
           → Условие подтверждено → Исполнение → Закрыта
           → Условие не наступило → Откат → Средства освобождены

Транш:   ожидает → собирается → собран → удерживается
         → релиз одобрен → выплачивается → выплачен
         → возврат одобрен → возвращается → возвращён

Выплата: создана → отправлена → {исполнена | отклонена | неизвестно}
         неизвестно → (только через сверку) → {исполнена | отклонена}
```

Интерфейс **не изобретает** новых состояний домена. Всё, что ниже — проекция этих
состояний на язык пользователя.

### 2.2 «Где деньги» — проекция для интерфейса

Это единственный источник истины для блока 1 кабинета покупателя, для карточки
подтверждения средств у продавца и для строки денег в консоли. Один код — один
смысл во всех трёх кабинетах, формулировки разные по роли.

| Код | Ключ состояния | Где деньги физически | Что дальше | Что от покупателя | Что видит продавец |
|---|---|---|---|---|---|
| `M-01` | `notFunded` | У покупателя, в его банке | Ждём перевод | Пополнить | Средства не внесены |
| `M-02` | `transferDeclared` | В пути между банками | Зачисление, срок {SLA} | Ничего, ждать | Перевод заявлен, не подтверждён |
| `M-03` | `unidentified` | Пришли на номинальный счёт, **не опознаны** (`suspense`) | Ручной разбор, срок {SLA} | Прислать подтверждение перевода | Средства не внесены (см. §8.4) |
| `M-04` | `heldThirdParty` | На номинальном счёте, **удержаны** | Разбор комплаенсом | Подтвердить родство/происхождение или согласовать возврат | Средства не внесены |
| `M-05` | `onAccountFx` | На счёте покупателя, в валюте перевода | Конвертация по курсу | Подтвердить курс | Средства внесены, не конвертированы |
| `M-06` | `onAccount` | На счёте покупателя, в лари | Резервирование в день подачи | Ничего / забрать в любой момент | Деньги у покупателя, ещё не зарезервированы |
| `M-07` | `partiallyFunded` | Часть на счёте | Добор до ⏱, иначе откат | Дослать {разница} | Собрано {X} из {Y} |
| `M-08` | `overfunded` | На счёте с излишком | Излишек вернём после закрытия/отмены на счёт-источник | Ничего | Сумма собрана |
| `M-09` | `reserved` | На номинальном счёте, **зарезервированы под сделку** | Подача документов, ⏱ | Ничего, ждём подачу | **СРЕДСТВА ПОДТВЕРЖДЕНЫ** |
| `M-10` | `submitted` | Там же, резерв держится | Подтверждение регистрации, ⏱ | Ничего | Документы поданы, резерв держится |
| `M-11` | `releasePending` | Там же | Расчёт исполняется | Ничего | Регистрация подтверждена, расчёт готовится |
| `M-12` | `released` | **У получателя** | Сделка закрывается | Ничего | Расчёт исполнен |
| `M-13` | `payoutUnknown` | Поручение отправлено, подтверждение банка не получено | Сверка следующего банковского дня | Ничего, мы сообщим | Поручение отправлено, ждём подтверждение банка |
| `M-14` | `rollbackInProgress` | На номинальном счёте, резерв снимается | Возврат на счёт покупателя | Ничего | Условие не наступило, резерв снимается |
| `M-15` | `releasedToAccount` | **На счёте покупателя**, свободны | Вывод или новая сделка | Забрать или провести сделку заново | Сделка не состоялась |
| `M-16` | `refundInProgress` | Возврат на счёт-источник в пути | Зачисление в его банке | Ничего | — |
| `M-17` | `refunded` | **У покупателя, в его банке** | Ничего | Ничего | — |
| `M-18` | `frozen` | Где были, движение приостановлено | Разбор, срок | По ситуации | Операции приостановлены |

Модификаторы, накладываемые поверх любого состояния (не заменяют его):

| Модификатор | Смысл | Влияние на интерфейс |
|---|---|---|
| `clockPaused` | Часы сделки остановлены (реестр недоступен) | Таймер замирает, показана причина, все дедлайны помечены «срок будет пересчитан» |
| `quoteExpired` | Окно фиксации курса истекло | Блокирующая карточка пересчёта, суммы в лари скрыты до подтверждения нового курса |
| `requisitesLocked` | Реквизиты выплаты заблокированы резервом | В кабинете получателя форма read-only |
| `requisitesCooling` | Идёт период охлаждения после смены реквизитов | Выплата запрещена, таймер охлаждения виден обеим сторонам |
| `coverageBreach` | Нарушено покрытие клиентских средств | Приём новых сделок остановлен; в кабинетах — баннер о приостановке приёма, **без деталей инцидента** |

**Диаграмма переходов (упрощённая, для интерфейса):**

```
M-01 ──заявил перевод──▶ M-02 ──зачислено, референс распознан──▶ M-05
  │                        │
  │                        ├──референс не распознан──▶ M-03 ──опознано──▶ M-05
  │                        └──отправитель ≠ покупатель──▶ M-04 ──разбор──▶ M-05 | M-16
  │
M-05 ──конвертация──▶ M-06 ──▶ M-07 (недобор) ──добор──▶ M-06
                       │  └──▶ M-08 (переплата)
                       │
                       ├──резерв──▶ M-09 ──подача──▶ M-10
                       │                               ├──условие подтверждено──▶ M-11 ──▶ M-12
                       │                               │                                └──▶ M-13 ──сверка──▶ M-12 | M-14
                       │                               └──дедлайн, условие не наступило──▶ M-14 ──▶ M-15
                       │
                       └──вывод──▶ M-16 ──▶ M-17

M-15 ──вывод──▶ M-16      M-15 ──новая сделка──▶ M-09
Любое ──стоп комплаенса──▶ M-18 ──▶ возврат в исходное или M-16
```

**Тупиков нет:** из каждого состояния есть выход, и для каждого выход по
бездействию — возврат покупателю (красная линия №7). Состояния `M-13` и `M-18`
не имеют автоматического выхода по таймеру — из них выходят только через сверку
или решение человека, и интерфейс это говорит прямо.

### 2.3 Матрица «состояние сделки × главный экран покупателя»

Читается как контракт: для каждого состояния сделки известно, что показывает
каждый из семи блоков. Детали блоков — §3.3.

| Сделка | Блок 1 «где деньги» | Блок 2 «что требуется» | Блок 3 лента | Блок 6 срок и последствие |
|---|---|---|---|---|
| Черновик | `M-01` | Пройти проверку личности | шаг 1 текущий | Нет дедлайна → блок скрыт, вместо него «срок появится после…» |
| Стороны проверены | `M-01` | Ждать проверки объекта | шаг 2 текущий | То же |
| Объект проверен | `M-01` | **Пополнить счёт** | шаг 3 текущий | Дедлайн пополнения → откат сделки |
| Средства заведены | `M-05`/`M-06`/`M-07`/`M-08` | Подтвердить курс / дослать / ничего | шаг 3 пройден | Дедлайн резерва |
| Зарезервированы | `M-09` | Ничего, ждём подачу | шаг 4 текущий | «Если не подадут до ⏱ — резерв снят, деньги остаются у вас» |
| Подано на регистрацию | `M-10` | Ничего, ждём реестр | шаг 5 текущий | «Если регистрация не подтвердится до ⏱ — резерв снят» |
| Условие подтверждено | `M-11` | Ничего | шаг 6 пройден | Срок исполнения расчёта |
| Исполнение | `M-11`/`M-13` | Ничего | шаг 7 текущий | Срок подтверждения банка |
| Закрыта | `M-12` | Ничего. Доступны документы | все пройдены | Блок срока заменён на дату закрытия |
| Условие не наступило | `M-14` | Ничего, идёт откат | шаг 5 не пройден, ветка отката | «Резерв снимается, деньги вернутся на ваш счёт до ⏱» |
| Откат / Средства освобождены | `M-15` | **Забрать деньги или провести сделку заново** | ветка отката завершена | Нет дедлайна. Есть срок хранения средств на счёте |

**Инвариант интерфейса:** транш в нетерминальном состоянии **всегда** имеет
видимый дедлайн. Если сервер вернул нетерминальный транш без дедлайна — это баг
домена (`FUNCTIONAL.md` §2.7); интерфейс показывает `⚠ common.deadline.missing`
и создаёт обращение автоматически, а не рисует пустоту **[решение]**.

### 2.4 Уровни подтверждения средств для получателя

Лестница, по которой продавец понимает, насколько прочна его позиция. Один
компонент ▣ C-08, пять уровней:

| Уровень | Условие | Что это значит для продавца |
|---|---|---|
| `A0` | Сделка заведена | Ничего пока не подтверждено |
| `A1` | Покупатель прошёл проверку | Покупатель существует и проверен |
| `A2` | Средства на счёте покупателя | Деньги есть, но принадлежат покупателю и отзывны |
| `A3` | **Средства зарезервированы под сделку** | Выдано подтверждение резервирования с номером |
| `A4` | Расчёт исполнен | Деньги ушли на его счёт |

Уровень **не** называется гарантией. Разница между `A2` и `A3` объясняется явно —
это ровно то, ради чего продавец приходит в кабинет.

# 3. Кабинет покупателя

**Устройство:** mobile-first, 360 px базовая ширина.
**Языки:** русский, английский, грузинский.
**Кто:** иностранец, часто вне страны, часто в другом часовом поясе, сумма для
него значительная, доверия к нам пока нет.

**[открыто]** Существует ли кабинет до заведения сделки оператором (`CABINETS.md`
§8.2). Ниже спроектировано в предположении **«кабинет появляется вместе со
сделкой»**: пользователь получает приглашение, входит и сразу видит сделку. Если
решение будет иным, добавляется экран «сделок пока нет» — он специфицирован в
§3.3/`SC-empty` как заготовка.

## 3.0 Информационная архитектура и каркас

```
┌──────────────────────────────────────┐
│ ▣ C-20 Шапка                         │
│  «buyer.nav.brand»   ⚙  🌐 RU|EN|KA  │   🌐 = ▣ C-21 переключатель языка
├──────────────────────────────────────┤
│                                      │
│           СОДЕРЖИМОЕ ЭКРАНА          │
│                                      │
├──────────────────────────────────────┤
│ ▣ C-05 Блок безопасности (постоянно) │
└──────────────────────────────────────┘
│ ▣ C-22 Нижняя навигация (xs–sm)      │
│  Сделка · Счёт · Документы · Помощь  │
└──────────────────────────────────────┘
```

Четыре пункта навигации, не больше: «Сделка», «Мой счёт», «Документы», «Помощь и
безопасность». Пополнение — **не пункт навигации**, а действие внутри сделки и
счёта: у него нет самостоятельного смысла вне контекста «сколько и зачем».
Проверка личности — не пункт, а перехватывающий мастер: пока она не пройдена,
любой экран, кроме помощи, ведёт на неё.

На `lg+` нижняя навигация превращается в горизонтальную в шапке; содержимое
ограничено по ширине (примерно 65 символов измерения строки) и остаётся одной
колонкой.

**Глобальные баннеры** (над содержимым, стек не более двух одновременно,
приоритет сверху вниз): приостановка операций (`M-18`), нарушение покрытия
(`coverageBreach`, текст без деталей инцидента), истёкшая фиксация курса,
требуется действие по проверке личности, часы приостановлены. ▣ C-13.

## 3.1 Экран B-01 — Вход

### Назначение
Впустить того, кого мы уже знаем, и не дать фишингу выглядеть так же.

### Данные
Способ входа (почта / телефон), одноразовый код, признак доверенного устройства,
язык интерфейса.

### Структура (`xs`)

```
┌──────────────────────────────────────┐
│ «buyer.brand.name»        🌐 RU EN KA│
│                                      │
│ H1 «buyer.login.title»               │
│ «buyer.login.subtitle»               │
│                                      │
│ [ Поле: «buyer.login.email.label» ]  │
│   «buyer.login.email.hint»           │
│                                      │
│ [[ «buyer.login.submit» ]]           │
│                                      │
│ ▸ «buyer.login.noAccess»             │
│    «buyer.login.noAccess.body»       │
│                                      │
│ ▣ C-05 Блок безопасности             │
│ «buyer.login.legal» ⚖                │
└──────────────────────────────────────┘
```

Второй шаг — ввод кода: ▣ C-23 OTP-поле, шесть ячеек, автоподстановка из SMS,
вставка целиком, обратный отсчёт до повторной отправки, счётчик оставшихся
попыток.

### Состояния

| Код | Условие | Поведение |
|---|---|---|
| `S-01` | Ввод идентификатора | Базовое |
| `S-02` | Код отправлен | Таймер повторной отправки; ключ `buyer.login.otp.resendIn` с плюрализацией секунд |
| `S-03` | Код неверен | Ошибка под полем, **введённое не стирается**, счётчик попыток виден с первой ошибки, а не с последней |
| `S-04` | Попытки исчерпаны | Временная блокировка с точным временем разблокировки (две зоны, §1.2), путь через поддержку |
| `S-05` | Учётной записи нет | **Не сообщаем, существует ли адрес.** Одинаковый ответ для существующего и несуществующего; «код отправлен, если адрес известен» |
| `S-06` | Вход из новой страны/устройства | Дополнительный фактор + уведомление на все каналы. Экран объясняет почему |
| `SC-error` | Сервис недоступен | «Вход временно недоступен, деньги в безопасности», статус-страница, номер обращения |
| `SC-frozen` | Учётная запись приостановлена | Впускаем, но кабинет в режиме чтения; причина и срок |

### Поведение и крайние случаи
- Ссылка из письма ведёт сюда, а не в действие (§1.6). После входа —
  восстановление намерения: сразу экран сделки.
- Переключатель языка доступен **до** входа и запоминается в устройстве до
  профиля.
- Вставка кода из буфера обмена не должна ломаться о шесть отдельных ячеек.
- Автозаполнение менеджеров паролей не блокируется.
- Экран не показывает ни сумм, ни имён сторон, ни названия объекта — вход виден
  тому, кто взял телефон.

### Адаптивность
Одна колонка на всех классах, максимум 400 px ширины формы, вертикально
по центру на `lg+`. Клавиатура на `xs` не перекрывает кнопку: она в потоке, не
`position: fixed`.

### Доступность
`autocomplete="one-time-code"`, `inputmode="numeric"`; ошибка связана с группой
ячеек, а не с отдельной ячейкой; таймер повторной отправки в `aria-live=polite`.

### Компоненты
C-05, C-14, C-20, C-21, C-23, C-24 (поле), C-25 (кнопка).

## 3.2 Экран B-02 — Проверка личности

### Назначение
Собрать то, без чего сделка не начнётся, не потеряв клиента на середине. Это
самый длинный и самый бросаемый путь в продукте.

### Форма — пошаговый мастер

| Шаг | Содержание | Может быть отложен |
|---|---|---|
| 1 | Документ, по возможности NFC-чтение чипа | нет |
| 2 | Селфи с проверкой живости **или альтернатива** | нет, но есть второй путь |
| 3 | Адрес проживания | нет |
| 4 | Налоговое резидентство | нет |
| 5 | **Источник средств** | нет — но сохраняется по частям |
| 6 | Декларация о публичной должности ⚖ | нет |
| 7 | Обзор и отправка | — |

### Каркас мастера

```
┌──────────────────────────────────────┐
│ ← «buyer.kyc.back»      «шаг 3 из 7» │  ▣ C-26 индикатор шагов
│ ▓▓▓▓▓░░░░░░░  с подписями шагов      │
├──────────────────────────────────────┤
│ H1 «buyer.kyc.step3.title»           │
│ «buyer.kyc.step3.why»   ← зачем      │
│                                      │
│      ... поля шага ...               │
│                                      │
│ [[ «buyer.kyc.continue» ]]           │
│ [ «buyer.kyc.saveExit» ]             │
├──────────────────────────────────────┤
│ ▣ C-05                               │
└──────────────────────────────────────┘
```

**«Зачем» на каждом шаге** — не украшение. Иностранец отдаёт паспорт и выписку
по счёту незнакомому сервису; если не объяснить, зачем именно это нужно, он
уходит. Ключ `buyer.kyc.stepN.why`, копи-бриф: одна фраза, причина в терминах
закона и его же безопасности, без канцелярита, без «в соответствии с
требованиями законодательства» без указания какого.

### Сквозные состояния мастера

| Код | Условие | Поведение |
|---|---|---|
| `S-01` | Не начат | Экран-вход в проверку: сколько шагов, сколько времени займёт **[гипотеза: 12–20 минут, уточнить на пилоте]**, что подготовить заранее (список документов до старта, а не по ходу) |
| `S-02` | В процессе | Автосохранение каждого шага; выход и возврат без потери |
| `S-03` | Отправлено, на проверке | Экран ожидания: срок решения (норматив ≤4 рабочих часов, `PRODUCT.md` §13), что происходит, можно закрыть страницу |
| `S-04` | Нужны уточнения | **Не «отказ».** Список того, что заменить, с причиной по каждому пункту; остальное принято и не переделывается |
| `S-05` | Отклонено | Причина в допустимых пределах раскрытия ⚖, путь обжалования, что происходит с уже внесёнными деньгами (`M-16`) |
| `S-06` | Пройдено | Свёрнутая карточка в профиле, дата и срок следующей перепроверки |
| `SC-error` | Провайдер идентификации недоступен | Не теряем введённое; предлагаем альтернативу (видеозвонок) сразу, а не после трёх попыток |

### Шаг 1 — документ

- Выбор страны и типа документа → **список требований меняется**.
- NFC-чтение: анимированная инструкция «приложите документ к телефону», состояния
  `поиск / чтение / успех / чип не читается`. При неудаче — тихий переход к
  фотографированию, без обвинения пользователя.
- Съёмка: рамка, автоспуск при фокусе, немедленная проверка качества (блики,
  обрез, размытость) с конкретной причиной переснять — не «плохое фото».
- Крайние случаи: документ без MRZ; два гражданства (какой документ выбрать —
  подсказка); срок действия истекает в ближайшие 3 месяца → предупреждение до
  загрузки, а не после проверки; имя в документе латиницей ≠ имени в профиле →
  §5.4, поле `nameAsInDocument` фиксируется отдельно.

Альтернатива **видна сразу**, а не после провала. Копи-бриф

### Шаги 3–4 — адрес и налоговое резидентство

Обычная форма, правила §1.7 и `form-design`: одна колонка, метки сверху,
валидация на потере фокуса, помеченное необязательное (не обязательное).

Самый тяжёлый шаг. Проектируется как последовательность вопросов, а не как
загрузчик файлов. Ошибка «клиент грузит не то → цикл повторяется» стоит нам
4–8 человеко-часов и клиенту недели.

Показ покрытия клиенту — **[решение]**: правило «подтверждённое происхождение
закрывает не менее 90% суммы» (`CABINETS.md` §5.2) объясняет клиенту, почему
недостаточно одной справки, и превращает шаг из бюрократии в понятную задачу.
Риск: подсказывает, как подогнать. Смягчение: показываем **порог покрытия**, но
не показываем, какие именно детекторы сработали. Вынесено в §8.5.

**5.3 — Что приложить именно для этого типа.**

Для каждого выбранного типа — свой экран со своим списком. Не общий загрузчик.

```
┌──────────────────────────────────────┐
│ «источник 2 из 3»                    │
│ H1 «buyer.sof.doc.propertySale.title»│
│ «buyer.sof.doc.propertySale.intro»   │

│ ┌──────────────────────────────────┐ │
│ │ 1 «...contract.title»            │ │
│ │   «...contract.whatMustBeVisible»│ │
│ │   ▸ «common.doc.showExample»     │ │
│ │   [ Загрузить ]  ● не приложено  │ │
│ ├──────────────────────────────────┤ │
│ │ 2 «...bankCredit.title»          │ │
│ │   «...bankCredit.whatMustBeVisible»│
│ │   ✓ принято · {файл} · {дата}    │ │

│ │ 3 «...proofOfOwnership.title»    │ │
│ │   ⟳ на проверке                  │ │

```

Ключевые элементы каждого требования (▣ C-28):

- **что это за документ** — название на языке страны клиента, не наш термин;
- **что на нём должно быть видно** — «сумма, дата, ваше имя, название банка,
  печать или электронная подпись». Это то, что снимает половину повторов;
- **пример** — раскрывающийся образец с закрашенными данными; не модальное окно
  поверх формы, а раскрытие в потоке, чтобы можно было смотреть и загружать;
- **статус**: не приложено / загружается / на проверке / **принято** / **нужно
  заменить** (с конкретной причиной и указанием, что именно не видно);
- **необязательные** помечены явно, обязательные — нет (правило `form-design`).

Списки требований по типам источника — **данные, а не вёрстка**: конфигурация
с версией, ключи вида `buyer.sof.doc.<type>.<docId>.*`. Комплаенс меняет списки
без релиза фронтенда **[решение]**.

**5.4 — Связка «ваше имя ↔ движение денег».**

`FUNCTIONAL.md` требует связать имя покупателя с движением денег. Отдельный
короткий шаг: «покажите выписку, где видно поступление этой суммы на ваш счёт» с
объяснением, зачем — иначе клиент воспринимает это как повторный запрос того же.

**Состояния шага 5**

| Код | Условие | Поведение |
|---|---|---|
| `S-01` | Ничего не выбрано | Кнопка «дальше» недоступна с причиной рядом, не молча серая |
| `S-02` | Покрытие < порога | Предупреждение до отправки: «объяснено {X}% — этого не хватит», с предложением добавить источник. Отправить всё равно можно **[решение]**: запрещать нельзя, иначе клиент застревает без выхода |
| `S-03` | Документ отклонён | Красный статус у **конкретного** требования, причина, остальные не сбрасываются |
| `S-04` | Файл не того формата/размера | Ошибка до загрузки, лимиты названы заранее |
| `S-05` | Документ на языке, который мы не читаем | Просим перевод; список принимаемых языков назван заранее, а не после отказа **[открыто §8.6]** |
| `S-06` | Загрузка прервалась | Возобновление, файл не теряется, прогресс по каждому файлу отдельно |
| `S-07` | Всё принято | Шаг сворачивается в строку с галочкой; вернуться и посмотреть можно, менять — через обращение |

### Шаг 6 — декларация о публичной должности ⚖

Формулировки — через `legal-compliance-ru`. Интерфейсно: вопрос с вариантами
«нет / я / мой родственник или близкий», раскрытие полей только при «да»,
объяснение, что «да» не означает отказ, а означает дополнительные вопросы. Это
важно: без этой фразы люди отвечают неправдиво.

### Шаг 7 — обзор

Все ответы одним списком с возможностью вернуться к каждому. Согласия ⚖
отдельными чекбоксами (не одним общим), каждое со ссылкой на полный текст,
версия согласия фиксируется. Кнопка отправки — единственная.

### Адаптивность
Мастер одноколоночный на всех классах. На `lg+` — индикатор шагов слева
вертикально, содержимое справа, ширина содержимого не растёт. Камера и NFC —
только мобильный путь; на десктопе предлагается продолжить с телефона по
защищённой ссылке (одноразовая, короткоживущая, без данных в URL).

### Доступность
Каждый шаг — свой `<h1>` и заголовок документа; при переходе фокус ставится на
заголовок шага; прогресс объявляется как «шаг N из 7, {название}»; загрузка
файлов доступна кнопкой; статусы документов — текст + иконка, не только цвет.

### Компоненты
C-05, C-09, C-13, C-14, C-24…C-29, C-32 (загрузка файла), C-33 (образец
документа).

## 3.3 Экран B-03 — Сделка (главный)

### Назначение
Единственный экран, ради которого клиент заходит. Отвечает на три вопроса без
скролла в первом экране и без вкладок целиком.

**Решение о структуре:** один вертикальный экран, семь блоков, читается сверху
вниз **[установлено]**. Вкладок нет: вкладка прячет состояние, а прятать
состояние денег запрещено.

### Данные экрана
Состояние сделки и транша; `M-*` состояние денег; суммы (сделки, на счёте,
комиссии, к получению продавцом) в минорных единицах; курс и окно фиксации;
дедлайн с последствием; данные объекта из реестра и из договора; стороны и их
уровни проверки; список документов; лента событий.

| `M-17` `refunded` | Деньги вернулись в ваш банк | Дата и сумма; что удержано и почему ⚖ | Сумма | Документ о возврате |
| `M-18` `frozen` | Операции по сделке приостановлены | Что деньги на месте и никуда не двигаются; что происходит разбор; срок; к кому обратиться | Сумма, помечена как недоступная | Номер обращения |

**Отдельно про откат.** Три состояния отката (`M-14 → M-15 → опционально M-16/
M-17`) — самое опасное место продукта с точки зрения доверия: клиент узнаёт, что
сделка не состоялась. Требования к блоку в этих состояниях:

- Слово «откат» в интерфейсе покупателя не используется — это наш внутренний
  термин. Используется «сделка не состоялась» / «резерв снят».
- Причина названа **фактом**, а не оценкой: «регистрация не подтвердилась до
  {дата, время}», не «продавец не успел».
- **Никакой вины.** Ни продавцу, ни покупателю.
- Сразу видно, **что удержано** и почему (спред на конвертации удерживается,
  если конвертация состоялась — `FUNCTIONAL.md` §4.4). Эта строка ⚖ и обязана
  совпадать с офертой дословно; она также обязана быть показана **до** сделки,
  а не в момент отката.
- Два действия равнозначны: вывести или провести заново. Мы не подталкиваем к
  повтору — подталкивание в момент разочарования читается как манипуляция.
- Ничего не исчезает: лента, объект, документы остаются доступны.

**Состояния загрузки и ошибки блока 1**

| Состояние | Поведение |
|---|---|
| `SC-load` | Скелет в форме карточки; **сумма скелетом, не нулём** |
| `SC-stale` | Данные из кэша: карточка помечена «на {время}», все действия недоступны с причиной |
| `SC-error` | Карточка не отрисовалась: «мы не смогли показать состояние средств; деньги в безопасности» + повтор + номер обращения. Экран остальными блоками работает |

### Блок 2 — «Что требуется от вас сейчас» ▣ C-02

**Ровно одно действие.** Не список, не «рекомендуем также». Если действий два —
показывается более срочное, второе уходит в блок, к которому относится.
Исключение единственное: `M-15`, где два исхода равноправны по смыслу и выбор за
клиентом.

Если действий нет — «Ничего, ждём {кого} — {чего именно}» с указанием ожидаемого
срока. Ключ `buyer.deal.action.waiting.<subject>`; **пустая формулировка «ждите»
без субъекта и срока запрещена**.

| Объект не проверен | — (ждём нас) | `...waiting.platform` |
| `M-01` | Пополнить счёт | `...topup.cta` |
| `M-02` | — (ждём банк) | `...waiting.bank` |

причиной / успех (кнопка заменяется результатом, не исчезает молча).

### Блок 3 — «Лента сделки» ▣ C-06

**[установлено]** Один компонент, три представления по роли. Покупатель видит
человеческие формулировки, не технические статусы.

```
✓ «buyer.timeline.step.kycDone»          {дата}
✓ «buyer.timeline.step.propertyChecked»  {дата}
✓ «buyer.timeline.step.fundsOnAccount»   {дата}
◉ «buyer.timeline.step.reserved»         ⏱ {до}
○ «buyer.timeline.step.submitted»
○ «buyer.timeline.step.registered»
○ «buyer.timeline.step.settled»
```

- Три вида шага: пройден (с датой), текущий (со сроком), предстоящий.
- Ветка отката показывается **как ветка, а не как ошибка**: при `M-14` шаги
  «регистрация» и «расчёт» помечаются непройденными, добавляются шаги «резерв
  снят» и «деньги на вашем счёте».
- Раскрытие шага даёт подробность: что произошло, когда, кто (роль, не имя
  сотрудника), ссылка на документ, если есть.
- Пауза часов отображается вставкой в ленту: «часы остановлены с {время},
  причина, срок будет пересчитан».
- Пустое состояние: минимум один шаг всегда есть (сделка заведена).

### Блок 4 — «Объект» ▣ C-07

Адрес, кадастровый код, площадь, текущий собственник **по данным реестра**, дата
выписки, актуальность («данные на {дата}»).

**Расхождение с договором показывается красным и блокирует переход дальше**
**[установлено]**. Интерфейсно:

```
⚠ «buyer.property.mismatch.title»
  ┌───────────┬──────────────┬──────────────┐
  │ поле      │ в договоре   │ в реестре    │
  ├───────────┼──────────────┼──────────────┤
  │ площадь   │ {68.4 м²}    │ {66.1 м²}    │
  │ собственник│ {…}         │ {…}          │
  └───────────┴──────────────┴──────────────┘
  «buyer.property.mismatch.whatNow»
```

Блокировка означает: блок 2 показывает не «пополнить», а «расхождение
разбирается»; действие пополнения недоступно **с причиной**. Крайние случаи:
данные реестра недоступны (показываем последнюю выписку с датой и явной пометкой
«не актуализировано»); обременение появилось после проверки — это отдельное
предупреждение, не «расхождение».

### Блок 5 — «Деньги» ▣ C-04

Единый формат везде, чтобы цифры не расходились между экранами **[установлено]**.

```
«buyer.money.dealAmount»        {217 000 ₾}
«buyer.money.onAccount»         {217 000 ₾}
──────────────────────────────────────────
«buyer.money.rate»    {1 USD = 2,71 ₾}
      ⏱ «buyer.money.rate.lockedUntil» {время, 2 зоны}
«buyer.money.fee»               {2 605 ₾}  ▸ из чего
«buyer.money.payeeReceives»     {214 395 ₾}
```

**[открыто §8.1]** Показывать ли комиссию отдельной строкой. Спроектировано с
раскрытием — это позиция `CABINETS.md` §8.1 и требование потребительского права;
раскрытие идёт со ссылкой «из чего состоит» (комиссия за организацию расчёта,
спред на конвертации — разные вещи и разный НДС, `FUNCTIONAL.md` §4.1).

Правила: суммы никогда не обрезаются; валюта всегда рядом с числом; курс всегда
с направлением («1 USD = X ₾», а не «2,71»); в состоянии `quoteExpired` суммы в
лари **скрываются**, а не показываются устаревшими.

### Блок 6 — «Срок» ▣ C-03

```
⏱ {31 августа, 18:00 (Тбилиси)}
   {17:00 по вашему времени}
   «common.deadline.remaining» {через 4 ч 12 мин}
   ─────────────────────────────────────────
   «common.deadline.consequence.rollback»
```

Последствия по типам дедлайна (ключи `common.deadline.consequence.*`):
`topup` — сделка не начнётся, деньги останутся у вас;
`reserve` — резерв будет снят автоматически, деньги останутся у вас;
`registration` — резерв снят, деньги останутся у вас, сделку можно провести
заново; `quote` — курс будет пересчитан, вы увидите новую сумму до подтверждения;
`cooldown` — изменение реквизитов вступит в силу.

Состояния: обычный · менее суток · менее часа (усиление + объявление
скринридеру) · **истёк, обработка идёт** (не «просрочен», а «срок наступил,
выполняется то-то») · **приостановлен** (часы стоят) · отсутствует (баг, см.
§2.3).

### Блок 7 — «Стороны и документы» ▣ C-10

Стороны: роль, отображаемое имя, **уровень проверки** (не персональные данные
второй стороны — покупатель не видит паспорт продавца). Документы: список с
типом, датой, действием «посмотреть». Просмотр — с водяным знаком, содержащим
идентификатор смотрящего и время, каждый просмотр логируется **[установлено]**;
перед первым просмотром — однократное объяснение, что просмотр фиксируется.

### Состояния экрана целиком

| Код | Поведение |
|---|---|
| `SC-load` | Скелет: каркас + блок безопасности сразу; блоки 1, 2, 6 — приоритет загрузки; блоки 3, 4, 7 — вторая волна |
| `SC-empty` | Сделок нет (если решение §8.2 будет «кабинет до сделки»): объяснение, что сделку заводит оператор, что можно сделать пока (пройти проверку), контакт |
| `SC-partial` | Не пришёл блок объекта или лента — локальная ошибка внутри блока с повтором; блоки 1, 2, 6 обязаны отрисоваться, иначе экран уходит в `SC-error` |
| `SC-error` | Полноэкранная ошибка с ответом на вопрос «где деньги» из кэша, если он есть, и явной пометкой, что это кэш |
| `SC-denied` | Нет доступа к сделке (сменился участник): что произошло, к кому обратиться |
| `SC-frozen` | Все действия недоступны с причиной; экран читаем полностью |
| Несколько сделок | Над блоком 1 — переключатель сделок (▣ C-30); при одной сделке переключатель не рендерится |

### Крайние случаи
- Сделка отменена оператором до пополнения — состояние показывается, история
  доступна, деньги `M-01`.
- Сделка с несколькими траншами (рассрочка, P2): блок 5 показывает график, блок 1
  — состояние **ближайшего активного транша**, с явной пометкой «транш 3 из 48».
- Покупатель участвует в двух сделках с одним объектом — переключатель обязателен,
  адрес в заголовке.
- Изменение реквизитов продавца во время сделки → баннер: расчёт приостановлен на
  период охлаждения, срок, что это защитная мера.
- Смена состояния во время просмотра: обновление без потери позиции скролла;
  если изменилось состояние блока 1 — короткое ненавязчивое выделение, без
  модального окна. Модальное окно поверх денег — только при `quoteExpired` и
  `M-18`.

### Адаптивность

| Класс | Поведение |
|---|---|
| `xs`–`sm` | Одна колонка, порядок как выше. Блоки 1+2 — первый экран без скролла на 360×640 |
| `md` | То же, ширина ограничена, боковые поля растут |
| `lg`+ | Одна колонка по центру; блоки 1, 2, 6 могут быть закреплены в липкой шапке при скролле (компактный вид ▣ C-01 `compact`) |

Липкая компактная версия блока 1 на `lg+` — **[решение]**: длинная лента уводит
состояние денег за экран, а это единственное, что не должно исчезать.

## 3.4 Экран B-04 — Пополнение

### Назначение
Провести трансграничный перевод так, чтобы деньги дошли с первого раза, с
распознанным референсом, от правильного плательщика, в понятной сумме.
Это экран, на котором продукт зарабатывает и на котором чаще всего ломается.

реквизиты номинального счёта (получатель, банк, IBAN, SWIFT, назначение,

### Калькулятор валюты ▣ C-11

- **Двунаправленный**: «я отправлю X» ↔ «должно получиться Y». Оба поля
  редактируемые, второе пересчитывается. Клиент думает и так и так.
- Ввод денег: числовая клавиатура, разделители групп по локали, вставка из буфера
  с очисткой форматирования, ноль не показывается плейсхолдером.
- Под калькулятором — **сколько нужно по сделке** и разница, если введённое
  меньше или больше. Разница — не ошибка, а информация: «этого хватит на
  {N}%», «останется излишек {сумма}».
- **Раскрытие состава** (`...breakdown`): рыночный курс, наш спред, комиссия за
  услугу. Раскрыто по требованию, но раскрытие есть всегда **[установлено]**.
- **Предупреждение о чужих комиссиях** (`...bankFees.warning`): банк-отправитель
  и корреспондент могут удержать своё, и до нас дойдёт меньше. Копи-бриф: назвать
  это прямо и объяснить, что делать (перевод с опцией «все расходы за счёт
  отправителя», где доступна). Без этого предупреждения мы получаем недоплату и
  спор на ровном месте. **[решение]** — предупреждение обязательно.
- Валюты: список ограничен теми, что мы принимаем; недоступные валюты видны с
  причиной, а не отсутствуют.

### Фиксация курса и таймер ▣ C-12

Состояния котировки:

| Код | Условие | Интерфейс |
|---|---|---|
| `Q-01` `fresh` | Окно > 10 мин | Курс, «зафиксирован до {время, 2 зоны}», остаток крупно, но не мигает |
| `Q-02` `expiringSoon` | ≤ 10 мин | Усиление, обратный отсчёт мм:сс, кнопка «обновить курс» появляется заранее |
| `Q-03` `expired` | Окно истекло | Суммы в лари **скрыты**, не показаны устаревшими. Карточка: «курс истёк, обновите, чтобы увидеть актуальную сумму». Введённое в калькулятор сохраняется (WCAG 2.2.1) |
| `Q-04` `requoting` | Идёт запрос новой | Скелет вместо сумм, кнопка в состоянии «в работе» |
| `Q-05` `requoted` | Новая котировка | **Явное сравнение**: было / стало / разница. Молча не подменяем **[установлено]** |
| `Q-06` `unavailable` | Провайдер котировок недоступен | Реквизиты показываем, суммы в лари — нет; честно: курс определится при зачислении, вы увидите его до конвертации и сможете отказаться. **[открыто §8.7]** |
| `Q-07` `moneyArrivedAfterExpiry` | Деньги пришли, окно истекло | **Блокирующая карточка** на экране сделки: новая сумма, было/стало, два действия — принять новый курс или вернуть деньги на счёт-источник. До решения деньги не конвертируются и лежат в `M-05` |

Таймер: не единственный носитель информации — рядом абсолютное время. Истечение
не приводит к потере данных и не выполняет действий за пользователя.

### Реквизиты и референс ▣ C-16

- Каждое поле копируется отдельно одним нажатием; область нажатия — вся строка,
  не только иконка (≥44 px).
- Подтверждение копирования — короткое, не перекрывает поле.
- **Референс визуально выделен** сильнее остальных полей и вынесен в собственную
  рамку: это единственное, потеря чего стоит клиенту недели.
- Предупреждение `...reference.warning` — постоянное, не сворачиваемое: копи-бриф
  — перевод без референса не потеряется, но **задержится на ручной разбор**;
  назвать ожидаемый срок разбора. Пугать нельзя, скрывать нельзя.
- Формат референса: только латиница и цифры, без символов, неоднозначно
  читаемых (0/O, 1/I), группами по 4 **[решение]** — его переписывают руками в
  форму банка.
- «Отправить реквизиты на почту» — допустимо: письмо содержит реквизиты, но
  **не содержит ссылок на действия** (§1.6) и содержит блок безопасности.
  **[открыто §8.8]**: не противоречит ли это правилу «единственное место, где вы
  видите реквизиты — кабинет».
- Печать/PDF-версия платёжного поручения для похода в отделение банка — нужна
  сегменту, который платит из отделения **[решение]**, генерируется на языке
  клиента + английский дубль полей.
- Скриншот не запрещаем — запрещать бессмысленно; вместо этого водяной знак на
  PDF.

### Правило плательщика ▣ C-05b

**Показывается до перевода, а не после отказа** **[установлено]**.

- Позиция: **над** реквизитами, не под ними, не в подвале.
- Не сворачивается.
- Копи-бриф: отправитель обязан совпадать с вами; перевод от другого лица будет
  остановлен — **включая супруга, родителей и вашу компанию**, если не
  согласовано заранее; что делать, если иначе не получается (обратиться заранее);
  что происходит с остановленным платежом (не пропадает, разбирается, может быть
  возвращён отправителю).
- Чекбокс подтверждения `...payerRule.confirm` обязателен перед кнопкой «я
  отправил перевод». **[решение]** Чекбокс не закрывает доступ к реквизитам —
  реквизиты видны сразу; он подтверждает осведомлённость при заявлении перевода.
  Прятать реквизиты за чекбокс — лишнее трение на ровном месте.

### Статус зачисления ▣ C-15

```
┌──────────────────────────────────────┐
│ «buyer.topup.status.title»           │
│ ● «...declared» {дата}               │
│ ○ «...received»                      │
│ ○ «...credited»                      │
│ «...eta» {ожидаем до 2 сентября}     │
│ ▸ «...delayed.help»                  │
└──────────────────────────────────────┘
```

| Состояние | Что показываем |
|---|---|
| Не заявлен | Блок не показывается |
| Заявлен, ждём | Три шага, ожидаемый срок диапазоном (не точкой), «мы сообщим сами» |
| **Задержка** (срок вышел) | Спокойно, без тревоги: что бывает и почему (корреспондент, проверка банка, выходные в другой стране); что сделать — прислать подтверждение перевода из своего банка (кнопка загрузки); что делаем мы; когда следующее обновление. **Обязателен номер обращения** |
| Поступило, не опознано (`M-03`) | См. блок 1; здесь — действие «прислать подтверждение» |
| Поступило от третьего лица (`M-04`) | Объяснение + путь |
| Зачислено | Успех, сумма, переход к сделке; **если сумма отличается** — показываем разницу и следующий шаг (`M-07`/`M-08`) |
| Возвращено банком-корреспондентом | Отдельное состояние: деньги вернулись отправителю, причина, что делать |

### Способы пополнения ▣ C-31
Банковский перевод — по умолчанию и рекомендован. Pay-by-bank — где доступен
(доступность зависит от страны банка клиента; недоступность объясняется).
Карта — видна только при сумме ниже порога; выше порога **вариант присутствует в
списке с объяснением, почему недоступен** — иначе клиент ищет карту глазами и не
понимает, куда она делась. Копи-бриф: коротко и без извинений — на суммах такого
размера комиссия за карту несоразмерна.

### Состояния экрана

`SC-load` — скелет калькулятора, реквизиты не показываются до подтверждения
сервером (ошибочные реквизиты хуже отсутствующих).
`SC-error` при недоступности реквизитов — прямой текст: не показываем реквизиты
из кэша **никогда** **[решение]**, потому что подмена реквизитов — основной
вектор атаки, а кэш — это то, что могло устареть.
`SC-denied` — пополнение недоступно (сделка закрыта / комплаенс-стоп): причина,
куда обратиться.
`SC-frozen` — реквизиты скрыты, объяснение.

### Адаптивность
Калькулятор на `xs` — два поля вертикально с кнопкой переворота между ними; на
`md+` — в строку. Реквизиты — всегда список «метка / значение / копировать»
вертикально: таблица в две колонки на 360 px ломает IBAN. Липкая кнопка «я
отправил перевод» на `xs` не перекрывает последнее поле реквизитов.

### Доступность
Копирование сообщает результат в `aria-live`; таймер котировки — `polite`, за
минуту до конца — `assertive`; поля сумм с `inputmode="decimal"`; референс
объявляется по символам (`aria-label` с разделением), чтобы его можно было
записать со слуха.

### Компоненты
C-04, C-05, C-05b, C-11, C-12, C-13, C-14, C-15, C-16, C-31, C-32.

## 3.5 Экран B-05 — Мой счёт

### Назначение
Показать, что деньги остаются его собственными, пока не зарезервированы. Это
единственный экран, который делает разницу между «мы взяли ваши деньги» и «ваши
деньги на вашем счёте».

### Структура

```
┌──────────────────────────────────────┐
│ H1 «buyer.account.title»             │
│ ▣ C-04 Баланс                        │
│  «...available»   {217 000 ₾}        │
│  «...reserved»    {0 ₾}              │
│  ▸ «...otherCurrencies» {80 000 USD} │
│                                      │
│ [[ «buyer.account.withdraw» ]]       │
│  «buyer.account.withdraw.note»       │
│                                      │
│ «buyer.account.history»              │
│ ▣ C-17 Список движений               │
│  · {дата} «...op.topup»    +{сумма}  │
│  · {дата} «...op.fx»       ±{сумма}  │
│  · {дата} «...op.reserve»   {сумма}  │
│  · {дата} «...op.settle»   −{сумма}  │
└──────────────────────────────────────┘
```

### Состояния кнопки вывода — центральный элемент экрана

| Код | Условие | Что видит клиент |
|---|---|---|
| `W-01` | Средства свободны, счёт-источник известен | Кнопка активна. Подпись: вывод только на счёт-источник, на ваше имя |
| `W-02` | Часть зарезервирована | Кнопка активна на свободную часть; суммы разделены явно |
| `W-03` | **Зарезервировано** | Кнопка заменяется строкой «Средства зарезервированы до ⏱» + объяснение, почему нельзя, и когда снова будет можно **[установлено]**. Это не «серая кнопка», а другой элемент |
| `W-04` | Счёт-источник неизвестен (денег ещё не было) | Вывода нет, потому что выводить некуда и не на что; объяснение |
| `W-05` | Комплаенс-стоп | Недоступно, причина, номер обращения |
| `W-06` | Вывод в процессе | Статус, срок, невозможность отменить после отправки — сказано до подтверждения |
| `W-07` | Несколько счетов-источников | Выбор из них; **произвольные реквизиты ввести нельзя** (красная линия №9) |

Форма вывода: сумма (с «вывести всё»), счёт-источник (только выбор), подтверждение
вторым фактором, экран обзора перед отправкой (правило `form-design` для
высокорисковых форм), после отправки — статус, а не пустота.

### История движений ▣ C-17
Дата, тип операции (человеческим языком, не кодом счёта), сумма со знаком,
валюта, состояние, ссылка на сделку и на документ. Фильтр по типу и периоду.
Пустое состояние: «движений пока нет» + что появится после первого пополнения.
**Конвертация показывается двумя строками** (списание валюты, зачисление лари) с
курсом — одна строка со «спрятанным» спредом читается как обман.
Экспорт — CSV/PDF (маркирован водяным знаком).

### Крайние случаи
Отрицательный баланс невозможен по инварианту; если пришёл — показываем ошибку
данных и обращение, а не минус. Валюта, в которой мы больше не принимаем, —
остаток виден, пополнение недоступно с объяснением. Остаток ниже стоимости
перевода — предупреждение до вывода, что комиссия банка съест сумму.

### Адаптивность
`xs` — карточки движений (дата и сумма в одной строке, тип второй строкой), не
таблица. `md+` — таблица с фиксированной первой колонкой даты.

### Компоненты
C-04, C-05, C-14, C-17, C-25, C-30, C-34 (форма вывода).

## 3.6 Экран B-06 — Документы

### Назначение
Дать доступ к документам сделки и объяснить, что каждый просмотр фиксируется.

### Данные
Тип документа, сторона-источник, дата, состояние (действителен / заменён /
на проверке), доступность для роли.

### Структура
Список, сгруппированный по смыслу: по сделке · по объекту · мои документы
(проверка личности) · документы платформы (оферта, подтверждения, отчёты).
Каждый элемент: название, дата, размер, статус, действие «посмотреть».

### Поведение
- Просмотр — во встроенном просмотрщике **с водяным знаком** (идентификатор
  смотрящего + время) **[установлено]**. Скачивание, где разрешено, — с тем же
  знаком.
- Перед первым просмотром — однократное объяснение: просмотр фиксируется в
  журнале; это защищает вас и нас.
- Клиент видит **свой** журнал просмотров: когда он сам смотрел. Видит ли он, что
  документ смотрел кто-то ещё — **[открыто §8.9]**.
- Документы второй стороны, содержащие персональные данные, недоступны; в списке
  видны как «документ второй стороны — недоступен» с причиной, а не отсутствуют.

### Состояния
`SC-empty` — документов нет: что появится и когда.
`SC-load` — скелет списка; просмотрщик грузится с индикатором и возможностью
отмены (крупные PDF).
`SC-error` — файл не открылся: повтор, альтернатива (скачать), обращение.
`SC-denied` — нет прав на этот документ: причина, кто может выдать.
Файл повреждён / формат не поддерживается — отдельные состояния, не общая ошибка.

### Адаптивность
На `xs` просмотрщик — полноэкранный, с явной кнопкой возврата; зум жестами;
водяной знак масштабируется вместе с документом и остаётся читаемым.

### Компоненты
C-05, C-14, C-17, C-18 (просмотрщик), C-19 (бэдж статуса документа).

## 4.1 Экран R-01 — Подтверждение средств (главный экран продавца)

### Назначение
**Заменить продавцу владение деньгами.** От того, поверит ли он этой карточке,
зависит, пойдёт ли он к нотариусу отдавать квартиру. Это самый важный экран
кабинета получателя и, вероятно, всего продукта.

### Что делает карточку убедительной

Проектные принципы, из которых собрана анатомия:

1. **Названа сумма, названо место.** Не «средства обеспечены», а сумма + банк +
   тип счёта. Абстракция не убеждает.
2. **Назван момент.** Дата и время установления резерва с зоной — событие, а не
   состояние.
3. **Оба исхода показаны рядом, симметрично.** Продавец должен увидеть и плохой
   исход тоже — карточка, показывающая только хороший, читается как реклама.
4. **Названо, сколько он получит на руки**, а не сумма сделки. Вычеты построчно.
5. **Проверяемость.** У подтверждения есть номер и документ, который можно
   показать нотариусу и юристу и проверить у нас по номеру.
6. **Названо, чего мы НЕ обещаем.** ⚖ Безотзывное поручение ничтожно
   (`PRODUCT.md` §11), поэтому карточка не имеет права говорить «покупатель не
   сможет забрать деньги». Она говорит, что резерв установлен, окно короткое, и
   что при бездействии деньги вернутся покупателю. Честная граница — то, что
   отличает нас от обещания, которое нельзя исполнить.
7. **Тот же язык, что у покупателя.** Обе стороны видят одни и те же цифры и
   один и тот же дедлайн (`C-04`, `C-03`), иначе первый же спор будет о том, кто
   что видел.

### Данные
Уровень подтверждения `A0…A4`; сумма резерва; банк-держатель и тип счёта; момент
резервирования; номер подтверждения; сумма к выплате и вычеты; реквизиты
(маскированные) и их статус; дедлайн и последствие; состояние сделки; ссылка на
документ подтверждения.

### Структура (`lg`)

```

├───────────────────────────────────────────────────────────────┤
│ ▣ C-37 КАРТОЧКА ПОДТВЕРЖДЕНИЯ СРЕДСТВ                         │
│                                                               │
│  H1 «payee.assurance.reserved.title»                          │
│                                                               │
│  {217 000 ₾}                                                  │
│  «payee.assurance.reserved.subtitle»                          │
│  «payee.assurance.reservedAt» {31 августа, 11:20 (Тбилиси)}   │
│  «payee.assurance.confirmationNo» {SD-CONF-7K42}   [⧉]        │
```

### Крайние случаи
- Несколько сделок у одного продавца → список сделок с карточками-превью
  (уровень, сумма, дедлайн), вход в полную карточку.
- Сумма изменена оператором (пересогласование) → карточка показывает «было/
  стало» и дату изменения, а не тихо новое число.
- Продавец смотрит с телефона у нотариуса — см. адаптивность; это основной
  сценарий использования карточки, а не побочный.
- Продавцу показали поддельный кабинет: карточка содержит номер подтверждения,
  проверяемый на публичной странице проверки; блок безопасности объясняет, как
  проверить.
- Сделка с несколькими получателями (доли) → каждый видит **свою** сумму к
  получению и общую сумму сделки, но не реквизиты другого.

## 4.2 Экран R-02 — Реквизиты выплаты (защитный периметр)

### Назначение
**[установлено]** Подмена реквизитов — самый вероятный сценарий атаки; 86% ущерба
от компрометации деловой переписки идёт через безотзывные переводы. Экран
проектируется как защитный периметр, а не как форма. Здесь трение — функция, а не
дефект.

### Принципы экрана

1. **Имя владельца счёта не вводится вручную.** Оно берётся из проверки личности
   и показывается как **нередактируемое** значение с объяснением. Это сильнее,
   чем сверка после ввода: не даёт даже попытки **[решение]**.
2. Вход в раздел — под свежим вторым фактором (не старше 5 минут).
3. Все действия — с задержкой и уведомлением, ни одно не мгновенно.
4. Экран всегда показывает, **что сейчас заблокировано и почему**, а не только
   поля.
5. История изменений реквизитов видна владельцу кабинета всегда.

### Форма ввода — правила

- Поля: страна банка → банк (справочник, поиск) → IBAN/номер счёта → SWIFT (если
  требуется) → **имя владельца (нередактируемое, из KYC)**.
- IBAN: маска по стране, валидация контрольного разряда **до** отправки, вставка
  из буфера с очисткой пробелов, проверка соответствия страны и банка.
- Повторный ввод IBAN во второе поле для сверки **[решение]** — да, это раздражает,
  но цена опечатки здесь — потеря шестизначной суммы. Вставка во второе поле
  запрещена (иначе сверка бессмысленна).
- Перед сохранением — **экран обзора** с полным IBAN, именем и банком крупно и
  вопросом «это ваш счёт?». Правило `form-design` для высокорисковых форм.
- Второй фактор — на сохранении, не на входе в форму (на входе — проверка
  свежести сессии).

### Уведомления при изменении
При переходе в `P-08` уведомление уходит **всем сторонам по всем каналам**
**[установлено]**. В кабинете покупателя появляется баннер: реквизиты получателя
меняются, расчёт приостановлен до {дата}, это защитная мера. В кабинете продавца
— строка «кто уведомлён», чтобы он понимал масштаб происходящего и не пытался
«по-тихому» поменять счёт.
На всех экранах, где показано изменение, есть действие **«это не я»** — оно
немедленно отменяет запрос и создаёт инцидент.

договоры, добавить реквизиты, проверить, что уведомления настроены). Пустой
дашборд как список задач, а не как отчёт с нулями.
`SC-partial` — метрики пришли, лента нет (или наоборот).
`SC-stale` — «данные на {время}», суммы помечены.
`SC-denied` — роль сотрудника без прав на суммы: метрики скрыты, задачи видны.

### Крайние случаи
Несколько проектов/юрлиц — фильтр по проекту, суммы никогда не смешиваются между
юрлицами без явного «все». Валюты — если поступления в разных валютах, метрика не
складывается в одно число, а показывается по валютам.

### Адаптивность
`lg+` — 5 метрик в строку; `md` — 3+2; `xs` — вертикальный список метрик,
несопоставленные первым блоком (на телефоне застройщик заходит именно за этим).

### Компоненты
C-04, C-05, C-13, C-41, C-42, C-43.

## 4.5 Экран R-11 — Договоры и юниты

### Назначение
Реестр объектов и договоров, импорт таблицей, карточка договора с графиком.

### Структура
Таблица ▣ C-44: юнит · договор · покупатель · сумма · оплачено · остаток ·
ближайший платёж · статус. Фильтры-чипы: статус, проект, просрочка, период.
Поиск по номеру договора, юниту, имени покупателя (по трём алфавитам, §5.4).

### Импорт таблицей — мастер ▣ C-45

| Шаг | Содержание | Состояния |
|---|---|---|
| 1 Загрузка | Файл, шаблон для скачивания, лимиты названы заранее | ошибка формата, слишком большой, пустой |
| 2 Сопоставление колонок | Наши поля ↔ его колонки, автоугадывание, предпросмотр первых строк | обязательное поле не сопоставлено — переход заблокирован с указанием какого |
| 3 Проверка | **Построчные ошибки и предупреждения** с номером строки и причиной; счётчики «принято / с ошибками / дубли» | 0 валидных строк; дубли; конфликт с существующими договорами |
| 4 Предпросмотр | Что именно будет создано и что обновлено | — |
| 5 Импорт | Прогресс, возможность уйти со страницы, уведомление о завершении | частичный успех — **отчёт с CSV непринятых строк для исправления** |

Импорт **никогда не молчаливо частичный**: результат всегда показан как «принято
N, отклонено M», с выгрузкой отклонённых.

### Карточка договора
Стороны, юнит, сумма, график платежей (таблица: номер, дата, сумма, статус,
фактическая дата, документ), история изменений, документы, действия (выгрузить,
запросить изменение).

### Состояния
`SC-empty` реестра — предложение импорта и ссылка на шаблон.
`SC-empty` результата фильтра — **отличается** от пустого реестра: «под фильтр
ничего не попало» + сброс фильтра.
`SC-error` импорта — файл сохраняется, шаг не теряется.

### Адаптивность
`xl` — все колонки; `lg` — приоритет+: скрываются «остаток» и «проект», доступны
в детали; `md` — карточки вместо строк; `xs` — карточки, поиск сверху, фильтры в
выдвижной панели. Суммы и даты не обрезаются никогда (§1.1).

### Компоненты
C-14, C-17, C-19, C-44, C-45, C-46 (фильтры), C-47 (пустое состояние).

## 4.6 Экран R-12 — Платежи и очередь несопоставленных

### Назначение
Лента входящих с автоматическим сопоставлением и **рабочая очередь
несопоставленных на виду**.

### Структура

```
┌───────────────────────────────────────────────────────────────┐
│ H1 «payee.dev.payments.title»                                 │
│ [ Все ] [ ⚠ Несопоставленные ⑦ ] [ Сопоставленные ] [ Возвраты]│
│                       ↑ вкладка по умолчанию, если очередь > 0 │
│ ▣ C-44                                                        │
│ ····{дата} {сумма} {отправитель} {референс} ▣C-48 {уверенность}│
│      [ Сопоставить ]                                          │
└───────────────────────────────────────────────────────────────┘
```

**[решение]** Если очередь несопоставленных не пуста — она открывается по
умолчанию. Открывать «все платежи», когда есть незакрытая работа, — прятать её.

### Разбор несопоставленного — панель ▣ C-49

```
┌─────────────────────────────┬─────────────────────────────────┐
│ ПЛАТЁЖ                      │ КАНДИДАТЫ                       │
│ {дата} {сумма} {валюта}     │ ◉ {договор} {юнит} {покупатель} │
│ Отправитель: {имя}          │   ▣ C-48 совпадение 82%          │
│ Назначение: {текст}         │   ✓ сумма  ✓ имя  ✗ референс     │
│ Референс: {не распознан}    │ ○ {договор} … 64%               │
│ ▸ полные данные платежа     │ ○ …                             │
│                             │ [поиск по договорам]            │
│                             │ [[«...proposeMatch»]]           │
│                             │ [ «...notOurs» ] [ «...ask» ]   │
└─────────────────────────────┴─────────────────────────────────┘
```

- Кандидаты ранжированы, у каждого — **почему он кандидат** (совпало/не совпало
  по полям), не только процент.
- **[открыто §8.3]** Является ли действие застройщика окончательным
  сопоставлением или предложением, которое подтверждает оператор. Спроектировано
  как **предложение**: `«...proposeMatch»`, после которого платёж переходит в
  «на подтверждении». Причина: веб-слой не двигает деньги, а сопоставление —
  основание зачисления. Если владелец решит иначе, меняется только копия ключа и
  состояние.
- «Это не наш платёж» — отправляет в наш разбор с комментарием.
- «Запросить уточнение» — запрос плательщику через нас, не напрямую (канал
  прямой переписки не создаём — §7 `CABINETS.md`).

### Состояния
`SC-empty` очереди — **хорошее состояние**: «несопоставленных нет» + когда
последний раз были + среднее время разбора. Пустая очередь должна выглядеть как
достижение, иначе люди не верят, что она работает.
Платёж уже разобран другим сотрудником — блокировка с указанием кто и когда.
Платёж от третьего лица — отдельная пометка и объяснение, что он удержан у нас.
Частичная сумма — предложение сопоставить как частичный платёж по графику.

### Адаптивность
`lg+` — две панели; `md` — панель кандидатов под платежом; `xs` — пошагово:
платёж → кандидаты → подтверждение.

### Компоненты
C-14, C-17, C-19, C-44, C-46, C-48, C-49.

## 4.7 Экран R-13 — Выплаты (застройщик)

### Назначение
Что и когда ушло на его счёт, с реестром для бухгалтерии.

### Данные
Дата, сумма, состав (какие платежи вошли), удержанная комиссия, состояние,
референс банка, документ.

### Структура
Таблица выплат; раскрытие строки → состав выплаты по платежам и договорам.
Кнопка выгрузки реестра. Сверху — ожидаемая ближайшая выплата с датой.

### Состояния
Выплата в состоянии «неизвестно» (`M-13`) — **показывается** с честной
формулировкой: поручение отправлено, подтверждение банка не получено, повтор не
производится, проверим по выписке. Скрывать нельзя: он всё равно увидит по своему
счёту, что денег нет.
Выплата отклонена банком — причина в понятных терминах, что делаем дальше, нужно
ли что-то от него (обычно да: проверить реквизиты).
`SC-empty` — выплат ещё не было: когда будет первая.

### Компоненты
C-04, C-14, C-17, C-19, C-44.

## 4.8 Экран R-14 — Отчёты

### Назначение
Выгрузка в формате, который принимает его учётная система **[установлено]**.

### Структура
Выбор отчёта (поступления, начислено против удержано, выплаты, договоры,
просрочка) → период → формат (CSV, XLSX, формат учётной системы **[открыто
§8.11]** — какой именно) → генерация.

### Поведение — длинная операция
Генерация может занимать минуты: паттерн фоновой задачи. Немедленный отклик
(«отчёт готовится»), возможность уйти со страницы, уведомление о готовности,
список последних отчётов со сроком хранения ссылок. Прогресс — определённый, если
известно количество строк; иначе — этапы, а не бесконечный спиннер.

### Состояния
Готовится · готов (ссылка со сроком жизни) · пустой результат (период без данных
— отдельное состояние, не ошибка) · ошибка генерации (повтор, обращение) ·
слишком большой период (лимит назван заранее, предложение разбить).

### Компоненты
C-14, C-17, C-25, C-46, C-50 (фоновая задача).
