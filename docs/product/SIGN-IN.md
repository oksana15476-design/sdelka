# Вход в систему: одноразовый код, сессия, выход

**Дата:** 2026-09-09 · **Статус:** реализовано; четыре развилки открыты
(`DECISIONS-REVIEW.md` §Z)

Документ описывает, **как это должно работать**, и рядом — чем именно это
сделано. Каждое утверждение помечено: **[установлено]** — проверено по коду или
первоисточнику, **[гипотеза]** — требует проверки, **[открыто]** — ответа нет.

---

## 0. Что было до захода **[установлено]**

Три дыры, каждая проверена чтением кода:

1. **Доказательства личности не существовало.** `establishSession`
   (`packages/auth/src/session.ts`) принимает `PrimaryAuthentication` и готовые
   подтверждения фактора, то есть личность **уже доказанную**. Функции, которая
   бы её производила, в дереве не было ни одной.
2. **Хранилища сессий не существовало.** `SessionStorePort` объявлен в том же
   файле, реализаций — ноль. Сессии жили в `World.sessions` — карте в памяти
   процесса. Перезапуск разлогинивал всех; вторая реплика не видела сессий
   первой. Таблица `sdelka.auth_session` при этом стояла в схеме с миграции
   `0010` со всеми триггерами и была пуста.
3. **Транспорта не существовало.** Ни маршрута, ни серверного действия: в
   `apps/web` не было ни одного `<input>`, кроме формы вывода средств, и ни
   одного пути `/login`.

`ACTORS.md` §12.1 строка 9 называет это прямо: «Аутентификация и сессия;
`allowedActions` с сервера — `apps/web`, размер M».

## 1. Флоу

### 1.1 Шаг «мне нужен код»

1. Человек открывает `/{язык}/login` и вводит **ключ учётной записи**.
2. Приложение (`packages/app/src/sign-in.ts`, `requestSignInCode`) ищет запись.
3. Запись есть → заводится **вызов** (`identity_challenge`): идентификатор,
   момент выдачи, срок, потолок попыток. Код **выводится** из вызова ключом из
   окружения и уходит в порт канала доставки. Отмечается момент доставки.
4. Записи нет → вызов **не заводится**, в журнал входов ложится отказ
   `auth.identity.account_unknown` с зарезервированным ключом `unresolved`
   вместо введённой строки.
5. Ответ в обоих случаях один: адрес `/{язык}/login?ref=<ссылка на вызов>`.

### 1.2 Шаг «вот код»

1. Форма отправляет ссылку на вызов и код.
2. `submitSignInCode` поднимает вызов, находит запись, зовёт `verifyChallenge`.
3. **Изменённое состояние вызова записывается до разбора исхода**: неверная
   попытка тратит попытку независимо от того, что решено дальше.
4. Совпало → `establishSession` по политике роли → сессия в
   `sdelka.auth_session` → `session_established` в журнал → кука → `/{язык}`.
5. Не совпало → `session_denied` с настоящей причиной в журнал → тот же экран с
   меткой `e=1`.

### 1.3 Выход

`/{язык}/logout`, форма (`POST`) → `signOut` → сессия отзывается (`revoked_at`),
`session_revoked` в журнал, кука снимается. Идемпотентен: выход из отозванной
или несуществующей сессии — тот же исход, а не отказ.

## 2. Правила

| # | Правило | Чем держится |
| --- | --- | --- |
| 1 | Код действует десять минут | `IDENTITY_CODE_POLICY.ttl`; сверху ограничено триггером базы получасом |
| 2 | Попыток пять | `IDENTITY_CODE_POLICY.maxAttempts`; в базе `max_attempts <= 10` и `attempts_used <= max_attempts` |
| 3 | Код принимается один раз | `consumedAt`; в базе — триггер: после отметки строка не меняется вовсе |
| 4 | Счётчик попыток идёт только вперёд | Триггер обновления: `db.auth.challenge_attempts_regression` |
| 5 | Срок вызова продлению не подлежит | Триггер обновления: `db.auth.challenge_immutable` |
| 6 | Кода нет ни в базе, ни в журнале | Колонки нет; код выводится `HMAC-SHA256` с ключом из окружения (`auth/src/code.ts`) |
| 7 | Ответ экрану один на все отказы | `uniformIdentityRejection`; настоящая причина — в журнал |
| 8 | Вход и отказ во входе оставляют запись | `sdelka.auth_event`; у роли приложения только `SELECT` и `INSERT` |
| 9 | Сессия переживает перезапуск процесса | `pgAuthStore` (`packages/db/src/store/auth.ts`) |
| 10 | Отзыв закрывает доступ немедленно | `sessionStatus` возвращает `revoked` в тот же момент; отозванная строка не оживает |

### 2.1 Почему код выводится, а не хранится **[установлено]**

Схема прямо запрещает колонку под секрет: `packages/db/test/auth-reference.test.ts`
(«секретов в схеме нет места») перечисляет запрещённые имена и требование
«пароль, семя TOTP, одноразовый код и приватный ключ не хранятся никак — ни в
открытом виде, ни в необратимом».

Запрет обоснован: отпечаток шестизначного кода перебирается за миллисекунды, то
есть «хранить хеш» здесь не защита, а её видимость. Поэтому код —
`HMAC-SHA256(ключ, идентификатор+запись+момент)` с усечением по RFC 4226 §5.3.
Ключ живёт в `SDELKA_AUTH_CODE_KEY` и больше нигде (красная линия №12).

### 2.2 Почему консольные роли так не входят **[установлено]**

`ACTORS.md` §11 Р6 вариант B забракован: канал, который может быть у
нападающего, вторым фактором не является. Политика консольной аудитории требует
второго фактора на входе и устойчивости к фишингу
(`CONSOLE_SESSION_POLICY`), а вход по коду её не даёт. Поэтому
`establishSession` отказывает консольной роли, и **консоль сегодня войти не
может вовсе**. Это верное состояние, а не пробел: устойчивого к фишингу канала
(`webauthn`) в продукте нет ни одного.

### 2.3 Кука сессии

`httpOnly`, `secure` (в боевом режиме), `sameSite=strict`, `path=/`, срок равен
сроку сессии. В куке только идентификатор: ни роли, ни имени, ни подписи —
всё остальное читается из базы по нему. Подписанная кука с полезной нагрузкой
была бы состоянием, которое **нельзя отозвать**, а отзыв здесь обязателен.

## 3. Порт канала доставки

Канал за портом `CodeDeliveryPort` (`packages/auth/src/delivery.ts`). Реализаций
две с половиной:

- **отладочная** — печатает код в журнал процесса. Собирается **только** в
  режиме `development`, в боевом бросает;
- **боевой адаптер** — **его нет ни одного**. Канал (почта, SMS, мессенджер) —
  отдельная интеграция, и по правилам проекта у неё сначала дизайн-док и
  груминг, потом код;
- `resolveCodeDelivery` в боевом режиме без адаптера **отказывает**.

Отказ виден снаружи процесса: `/health` отвечает `503` и полем
`auth: auth.code_delivery.adapter_missing`, то есть контейнер не становится
готовым и нагрузку не получает **[установлено]**, проверено запуском.

⚠ **Ворота стоят на готовности, а не в `register()`.** Первая редакция ставила
их в `instrumentation.ts` — сборка от этого падала целиком: Next собирает этот
файл и для среды `edge`, а туда по цепочке импортов приезжает `node:crypto`
(`@sdelka/domain/src/ids.ts`) и драйвер Postgres. Разрезать цепочку значит
переписать `@sdelka/domain` — чужой пакет. Обязательность самих переменных при
этом закрыта раньше: `pnpm env:check` не даёт запустить процесс без них.

## 4. Границы: кто что решает

| Слой | Что делает | Чего не делает |
| --- | --- | --- |
| `packages/auth` | Значения и правила: вызов, срок, попытки, однократность, политика сессии | Не ходит в сеть и в базу, не читает окружение |
| `packages/app` | Решение о входе: искать запись, засчитывать попытку, выдавать сессию, писать в журнал | Не знает ни про Postgres, ни про HTTP, ни про куки |
| `packages/db` | Хранилище: учётные записи, вызовы, сессии, журнал входов | Не содержит ни одного правила: они в схеме и в пакетах |
| `apps/web` | Транспорт: форма → вызов, результат → адрес, кука | **Не решает ничего** |

## 5. Крайние случаи

| Случай | Поведение |
| --- | --- |
| Учётной записи нет | Ответ по форме тот же, что у существующей; в журнале — отказ с ключом `unresolved` |
| Введена строка неверной формы (почта, телефон) | Запись не находится → тот же ответ; введённое значение в вечный журнал не попадает |
| Ссылка на вызов подделана | Вызов не находится → та же единая причина; исключения нет |
| Код введён с пробелами или дефисом | Пробелы и дефисы снимаются до сравнения |
| Код введён не цифрами | Не совпадает; попытка тратится |
| Истёкший вызов | Отказ; попытка **не** тратится — иначе истёкший вызов сам себя переводил бы в «исчерпано» |
| Повтор принятого кода | Отказ `auth.identity.challenge_consumed`; попытка не тратится |
| Канал не принял код | Наружу — та же единая причина; в журнале `auth.identity.channel_unavailable` |
| Перезапуск процесса | Сессия жива: она в базе |
| Выход дважды | Второй раз — тот же исход, второй записи в журнале нет |

## 6. Критерии приёмки

- [x] Истёкший код не пускает — `packages/auth/test/challenge.test.ts`,
      `packages/app/test/sign-in.test.ts`.
- [x] Исчерпанные попытки не пускают, и верный код после них тоже.
- [x] Повтор кода не даёт второй сессии.
- [x] Перезапуск процесса не теряет сессию — состояние живёт снаружи хранилища.
- [x] Отзыв закрывает доступ немедленно.
- [x] Ответ на «записи нет» и «код неверен» совпадает.
- [x] Кода и его отпечатка нет ни в значении вызова, ни в базе, ни в журнале.
- [x] Журнал входов не редактируется ролью приложения — живая попытка на базе.
- [x] Боевой режим без адаптера канала не считается здоровым.

## 7. Как проверить руками

```sh
export SDELKA_DB_PASSWORD=...            # пароль только из окружения
bash packages/db/scripts/dev-db.sh       # печатает строку подключения
export SDELKA_DATABASE_URL=...
pnpm db:migrate

psql "$SDELKA_DATABASE_URL" -c "SET ROLE sdelka_owner;
  INSERT INTO sdelka.auth_account (account_id, person_id, role_id, role_assigned_at)
  VALUES ('acc-smoke-1','per-smoke-1','party', now());"

export SDELKA_AUTH_MODE=development
export SDELKA_AUTH_CODE_KEY=$(head -c 32 /dev/urandom | base64)
pnpm --filter @sdelka/web build && pnpm --filter @sdelka/web start
```

Открыть `/ru/login`, ввести `acc-smoke-1`, взять код из журнала процесса
(строка `auth.code.delivered_to_log`), ввести. После входа — `/ru`, кука
`sdelka_session`. Дальше `/ru/logout`.

Записи смотреть так:

```sql
SELECT kind, account_id, reason::text FROM sdelka.auth_event ORDER BY event_seq;
SELECT attempts_used, consumed_at IS NOT NULL FROM sdelka.identity_challenge;
```
