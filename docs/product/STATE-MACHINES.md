# Стейт-машины: сделка, транш, выплата

**Версия:** 0.1 · **Дата:** 2026-08-31 · **Статус:** на приёмку владельцем
**Метод:** скилл `state-machine` — состояния, события, переходы, невозможные
состояния, guards, действия

---

## 0. Почему три машины, а не одна

Правило скилла: одна машина на одну заботу. У нас три разные заботы, и смешивание
их в один автомат — источник большинства ошибок в платёжных системах:

| Машина | Забота | Кто двигает |
|---|---|---|
| **Транш** | Жизненный цикл конкретных денег | События денег и условия |
| **Выплата** | Исполнение одного поручения во внешней системе | Ответы банка и сверка |
| **Сделка** | Оркестрация процесса и внешних шагов | Стороны, оператор, реестр |

Выплата вынесена отдельно **именно потому, что у неё есть состояние
«неизвестно»**, которого нет и не должно быть у транша. Если бы они были одной
машиной, сетевой сбой банка переводил бы деньги в неопределённость — а он не
должен.

## 1. Машина «Транш» — ядро

### 1.1 Состояния

| Состояние | Смысл | Терминальное |
|---|---|---|
| `pending` | Создан, денег нет | нет |
| `collecting` | Ожидается поступление, инструкции выданы | нет |
| `collected` | Деньги на счёте покупателя, его собственные и отзывные | нет |
| `reserved` | Зарезервированы под сделку, продавец видит подтверждение | нет |
| `release_pending` | Условие установлено, поручение формируется | нет |
| `release_blocked` | Расхождение или недостаток утверждений, ждёт человека | нет |
| `paying_out` | Поручение отправлено, ждём исход | нет |
| `paid_out` | Выплачено | **да** |
| `refund_pending` | Назначен возврат | нет |
| `refunding` | Возврат отправлен | нет |
| `refunded` | Возвращено покупателю | **да** |
| `written_off` | Списано вручную с двумя утверждениями и проводкой | **да** |

### 1.2 События

`funds_received(amount, sender, reference)` · `reserve_requested` ·
`reserve_expired` · `condition_established(evidence_bundle_id)` ·
`condition_failed` · `mismatch_detected(field)` · `approval_added(user_id)` ·
`operator_blocked(reason)` · `payout_result(settled|rejected|unknown)` ·
`reconciliation_resolved(settled|rejected)` · `deadline_reached` ·
`refund_requested(reason)` · `write_off_approved(user_id[2])`

### 1.3 Guards

| Guard | Проверяет |
|---|---|
| `g_amount_sufficient` | Поступившая сумма покрывает требуемую |
| `g_payer_matches` | Имя отправителя совпадает с покупателем |
| `g_evidence_present` | `evidence_bundle_id` не пуст |
| `g_fields_match` | Все пять полей выписки совпали |
| `g_owner_matches` | Собственник из реестра = продавец **по номеру документа** |
| `g_approvals_sufficient` | Число утверждений ≥ порога для этой суммы |
| `g_beneficiary_locked` | Реквизиты заблокированы и не менялись 72 часа |
| `g_no_active_payout` | Нет другой выплаты по этому траншу в активном статусе |
| `g_coverage_ok` | Покрытие клиентских средств равно единице |
| `g_source_account_known` | Известен счёт-источник для возврата |

### 1.4 Переходы

```
pending
  → collecting            [инструкции выданы]

collecting
  → collected             on funds_received
                          guard: g_amount_sufficient ∧ g_payer_matches
  → release_blocked       on funds_received
                          guard: ¬g_payer_matches            ← платёж третьего лица
  → refund_pending        on deadline_reached

collected
  → reserved              on reserve_requested
  → refund_pending        on refund_requested | deadline_reached

reserved
  → release_pending       on condition_established
                          guard: g_evidence_present ∧ g_fields_match
                                 ∧ g_owner_matches ∧ g_beneficiary_locked
  → release_blocked       on mismatch_detected
  → collected             on reserve_expired                 ← откат резерва
  → refund_pending        on condition_failed

release_pending
  → paying_out            guard: g_approvals_sufficient ∧ g_no_active_payout
                                 ∧ g_coverage_ok
  → release_blocked       on operator_blocked

release_blocked
  → release_pending       on approval_added ∧ расхождение снято
  → refund_pending        on refund_requested
  → collected             on reserve_expired

paying_out
  → paid_out              on payout_result(settled)
  → release_blocked       on payout_result(rejected)
  → paying_out            on payout_result(unknown)          ← остаётся здесь

refund_pending
  → refunding             guard: g_source_account_known
  → release_blocked       guard: ¬g_source_account_known      ← счёт-источник неизвестен

refunding
  → refunded              on payout_result(settled)
  → release_blocked       on payout_result(rejected)
  → refunding             on payout_result(unknown)

release_blocked
  → written_off           on write_off_approved(два разных пользователя)
```

### 1.5 Действия при входе и выходе

| Состояние | При входе | При выходе |
|---|---|---|
| `collected` | Проводка: Дт актив / Кт обязательство перед клиентом. Уведомление покупателю | — |
| `reserved` | Блокировка реквизитов получателя. Уведомление продавцу «средства подтверждены». Старт дедлайна | Снятие блокировки, если уходим не в выплату |
| `release_pending` | Формирование поручения с детерминированным ключом `uuid5(namespace, tranche_id)` | — |
| `paying_out` | Отправка поручения через исходящую очередь | — |
| `paid_out` | Проводки выплаты и комиссии **в одном журнале**. Уведомления обеим сторонам. Закрытие транша | — |
| `refunded` | Проводка возврата. Уведомление покупателю с указанием причины | — |
| `release_blocked` | Задача в очередь оператора с приоритетом по сумме. Уведомление сторонам о задержке | — |
| любое нетерминальное | Установка дедлайна | Проверка, что новое состояние тоже имеет дедлайн или терминально |

## 2. Машина «Выплата» — отдельная, потому что здесь легально «неизвестно»

### 2.1 Состояния и переходы

```
created
  → submitted             [поручение отправлено провайдеру]

submitted
  → settled               on provider_confirms
  → rejected              on provider_rejects
  → unknown               on timeout | network_error | ответ потерян

unknown
  → settled               on reconciliation_found_in_statement
  → rejected              on reconciliation_absent_from_statement
```

### 2.2 Правило, которое здесь главное

**Из `unknown` нет перехода в `created` или `submitted`.** Повтор невозможен без
прохождения через сверку с банковской выпиской.

Это единственная защита от двойной выплаты при сетевом сбое, и она реализуется
отсутствием перехода в автомате, а не проверкой в коде обработчика.

**Ни один адаптер не возвращает `rejected` при сетевой ошибке.** Только `unknown`.
Отказ — это явный ответ провайдера, а не отсутствие ответа.

## 3. Машина «Сделка» — оркестратор

Сделка не держит деньги. Она координирует стороны, объект, подачу и транши.

### 3.1 Состояния

| Состояние | Смысл | Терминальное |
|---|---|---|
| `draft` | Заводится оператором | нет |
| `parties_pending` | Идёт проверка сторон | нет |
| `property_pending` | Проверка объекта по реестру | нет |
| `ready` | Можно вносить деньги | нет |
| `funded` | Все транши собраны и зарезервированы | нет |
| `filed` | Подано на регистрацию, номер заявления зафиксирован | нет |
| `settling` | Условие установлено, идёт расчёт по траншам | нет |
| `settled` | Закрыта | **да** |
| `unwinding` | Идёт откат | нет |
| `unwound` | Откачена, средства освобождены | **да** |
| `cancelled` | Отменена до внесения денег | **да** |
| `frozen` | Заморожена комплаенсом или спором | нет |

### 3.2 Ключевые переходы

```
draft → parties_pending → property_pending → ready
ready → funded            [все транши в reserved]
funded → filed            on filing_registered(application_id)
filed → settling          on condition_established
      → unwinding         on condition_failed | deadline_reached
settling → settled        [все транши терминальны в paid_out]
unwinding → unwound       [все транши терминальны в refunded]

любое нетерминальное → frozen    on compliance_hold | dispute_raised
frozen → settling | unwinding    on unfreeze(два разных пользователя)
любое до funded → cancelled
```

### 3.3 Правило соответствия

Сделка не может быть в `settled`, пока хотя бы один транш не терминален. Это
инвариант, проверяемый на каждом переходе, а не порядок вызовов в коде.

## 4. Невозможные состояния, которые предотвращаем

Метод скилла требует перечислить их явно. Каждое закрывается структурой, а не
проверкой.

| Невозможное состояние | Чем предотвращается |
|---|---|
| Транш одновременно `paid_out` и `refunded` | Оба терминальны, переходов между ними нет |
| Две активные выплаты по одному траншу | Частичный уникальный индекс в базе |
| `reserved` без поступивших денег | Вход только из `collected` |
| `paying_out` без пакета доказательств | Guard `g_evidence_present` на переходе |
| Повтор выплаты после `unknown` | Отсутствие перехода в автомате |
| Выплата при покрытии меньше единицы | Guard `g_coverage_ok` |
| Выплата на реквизиты, изменённые вчера | Guard `g_beneficiary_locked` |
| Зачисление платежа от третьего лица на сделку | Guard `g_payer_matches`, уводит в `release_blocked` |
| Возврат на посторонний счёт | Guard `g_source_account_known` |
| Транш без дедлайна в нетерминальном состоянии | Проверка инвариантов каждые 15 минут |
| Утверждение той же учётной записью, что готовила | Проверка при добавлении утверждения |
| Отрицательный остаток клиентского счёта | Ограничение базы |
| Сделка `settled` при живом транше | Инвариант перехода |

## 5. Проверка на тупики

Правило скилла: у каждого состояния есть выход.

| Состояние | Выход | Гарантия выхода |
|---|---|---|
| `pending`, `collecting` | Дедлайн → `refund_pending` | Дедлайн обязателен |
| `collected` | Резерв или дедлайн | Дедлайн обязателен |
| `reserved` | Условие, отсечка или отказ | Отсечка рабочего дня |
| `release_pending` | Утверждения или блокировка | Задача в очереди с эскалацией |
| `paying_out`, `refunding` | Ответ провайдера или сверка | **Сверка ежедневная** — выход гарантирован не позднее следующего дня |
| `release_blocked` | Решение человека | Единственное состояние, где выход зависит от человека. Поэтому эскалация по возрасту и алерт при превышении норматива |
| `refund_pending` | Известен счёт-источник | Если неизвестен — уходит в `release_blocked` |
| `frozen` | Разморозка двумя людьми | Обязательный срок разбора |

**`release_blocked` — единственный настоящий риск тупика.** Он выходит только
действием человека. Поэтому: приоритет по сумме, эскалация по возрасту, алерт
дежурному, и метрика «возраст самой старой заблокированной сделки» на дежурном
дашборде.

## 6. Отображение состояний в интерфейсе

Правило скилла: каждое состояние имеет представление в интерфейсе. Одно состояние
— три формулировки по роли.

| Транш | Покупатель видит | Продавец видит | Оператор видит |
|---|---|---|---|
| `pending` | Ожидает создания | Сделка готовится | `pending` |
| `collecting` | Нужно внести деньги | Ожидаем поступление средств | `collecting`, дедлайн |
| `collected` | Деньги на вашем счёте, можете забрать | Средства поступили, не зарезервированы | `collected`, сумма |
| `reserved` | Зарезервированы под сделку до 18:00 | **Средства подтверждены и зарезервированы** | `reserved`, отсечка |
| `release_pending` | Регистрация подтверждена, готовим перевод | Регистрация подтверждена, готовим выплату | `release_pending`, утверждения |
| `release_blocked` | Требуется проверка, мы свяжемся | Требуется проверка | `release_blocked`, причина, приоритет |
| `paying_out` | Перевод отправлен | Выплата отправлена | `paying_out`, ключ, попытка |
| `paid_out` | Сделка закрыта | Деньги отправлены на ваш счёт | `paid_out`, проводки |
| `refund_pending` / `refunding` | Возвращаем средства | Сделка не состоялась | статус, причина |
| `refunded` | Деньги вернулись на ваш счёт | Сделка не состоялась | `refunded` |

Формулировки для клиента — это черновики. Финальные идут через связку копирайтер →
главред, как требует `CLAUDE.md`.

## 7. Что тестируется

Стейт-машина и учёт тестируются **без сети**. Если тесту нужен мок платёжного
провайдера — тест написан неверно: провайдер за портом, автомат работает на
событиях.

Обязательные тесты:

- Каждый guard: проходит и не проходит.
- Каждое невозможное состояние из раздела 4: попытка достичь его отвергается.
- Отсутствие тупиков: из любого нетерминального состояния достижимо терминальное.
- Идемпотентность: повторное событие с тем же ключом не меняет состояние дважды.
- Сумма проводок в журнале равна нулю на каждом переходе с деньгами.
- Свойство на случайных последовательностях событий: покрытие клиентских средств
  никогда не опускается ниже единицы и остаток счёта никогда не отрицателен.

Последний пункт — тест на свойствах, а не на примерах. Он ловит то, что не
приходит в голову при написании сценариев.

## 8. Ещё две машины, вынесенные отдельно

Не описаны здесь, но существуют как самостоятельные заботы: **проверка стороны**
(от заведения профиля до решения комплаенса) и **наблюдение оракула** (от
запуска проверки до пакета доказательств). Обе не двигают деньги и не должны
жить внутри автомата транша.
