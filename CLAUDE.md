# Рабочие правила для Claude (проект «Сделка»)

## Коммуникация

- **Claude ведёт разработку сам.** Батчи берём по приоритету автономно, без спроса
  разрешения. Владельца зовём на реальных развилках, где нужно его решение, и на
  итоговый «Пуш», когда накопились батчи.
- **Решения владельца фиксируем в документах** пометкой **[решение]**, чтобы через
  месяц было видно, что было выбрано осознанно, а что просто сложилось.
- **Не выдаём непроверенное за установленное.** В документах каждое утверждение
  помечается: **[установлено]** — проверено по первоисточнику,
  **[гипотеза]** — требует проверки, **[открыто]** — ответа нет, блокирует решение.
  Это правило дороже красоты текста: половина выводов первой волны исследований
  оказалась шаткой именно потому, что не была помечена.

## Процесс

- **Спека до реализации.** Каждая фича сопровождается функциональным описанием:
  флоу, состояния, правила, крайние случаи, критерии приёмки. Согласуется с
  владельцем ДО кода. Без спеки не начинаем.
- **Интеграции — отдельная проработка логики до кода.** Каждая внешняя интеграция
  (банк, платёжный провайдер, реестр, проверка личности, санкционный скрининг) —
  это целостная логика, а не тонкая заглушка. По каждой: сценарии, авторизация,
  маппинг сущностей, направление и триггеры синхронизации, идемпотентность,
  ошибки и повторы, безопасность и секреты, крайние случаи, критерии приёмки.
- Работать батчами: локально → QA после каждого батча → пуш по «Пуш» владельца.
- **Ветки:** работаем в назначенной ветке. Держать линию истории единой.

## Разделение работы

- **Весь UI — только через `design-agent` + UI-скиллы.** Экраны, состояния,
  компоненты, адаптивность.
- **Бэкенд, логика, тесты — через `development-agent`** по спеке-документу.
- **Весь пользовательский текст — через связку копирайтинг → главред.** Любой
  текст, который видит клиент: микрокопи интерфейса, уведомления, письма, тексты
  на сайте. Сначала `copywriter` (скиллы `brand-voice`, `ux-copy`,
  `content-creation`), затем `editor-in-chief` (скилл `brand-review`) — голос,
  ясность, единая терминология, грамотность, отсутствие ложных обещаний.
  Итерация до «принято» — только потом текст идёт в макет.
- **Юридически чувствительный текст — через `legal-compliance-ru`, не через
  главреда.** Оферта, согласия, политика обработки данных, раскрытие условий,
  формулировки условия расчёта.
- Итоговый QA и коммит-контроль — на мне.

## Три языка

Русский, английский, грузинский с первого дня.

- **Ни одной строки текста в коде.** Только ключи локализации, с первого коммита.
- **Грузинская версия оферты — основная.** Преддоговорная информация обязана быть
  на государственном языке — это требование потребительского закона.
- Макеты проверяются на самом длинном языке, а не на английском.
- Форматы чисел, дат и валют — через стандартный механизм локали, не своими
  функциями.
- Задел под правостороннее письмо: логические свойства в стилях вместо физических.

## Красные линии продукта

Нарушение любой из них — не баг, а инцидент.

1. **Клиентские средства одной сделки не финансируют обязательство по другой.**
   Архитектурный запрет, не дисциплина.
2. **Комиссия платформы не хранится на номинальном счёте** — выводится на
   операционный в момент расчёта, в том же журнале.
3. **Покрытие клиентских средств на конец банковского дня равно единице.**
   Отклонение останавливает приём новых сделок автоматически.
4. **Никаких сумм в плавающей точке.** Только целые минорные единицы.
5. **Выплата невозможна без ссылки на пакет доказательств.** Кнопки «просто
   выплатить» не существует.
6. **Условие расчёта привязано к внешнему факту**, а не к усмотрению платформы.
   Условие, зависящее только от воли сторон, делает сделку ничтожной.
7. **Состояние по умолчанию при бездействии — возврат покупателю**, не удержание.
8. **«Неизвестно» у выплаты — легальное состояние.** Повтор из него запрещён без
   прохождения через сверку.
9. **Возврат только на счёт-источник**, на имя плательщика.
10. **Слово «эскроу» не употребляется нигде** — ни в интерфейсе, ни на сайте, ни в
    договоре. Эскроу-агентом по закону может быть только банк или микробанк.
11. **Журнал аудита не редактируется.** Исправление — только новой записью со
    ссылкой на предыдущую.
12. **Секреты только из окружения.** Токены, ключи и реквизитные данные никогда не
    попадают в репозиторий.

## Инварианты, проверяемые базой, а не кодом

- Сумма проводок в журнале равна нулю — триггер.
- Не более одной выплаты по траншу в активных статусах — частичный уникальный
  индекс.
- Отрицательный остаток клиентского счёта невозможен.
- Транш в нетерминальном состоянии без дедлайна — ошибка, ловится проверкой.
- Роль приложения не имеет прав на изменение и удаление журнала аудита —
  проверяется грантами.

## QA перед коммитом

- `pnpm typecheck`, `pnpm test`, `pnpm build` — зелёные.
- Отдельно для денежного домена: тесты стейт-машины и учёта прогоняются без сети.
  Если для теста нужен мок платёжного провайдера — тест написан неверно.
- `git diff --check`.
- Отчитываемся о фактическом результате: если проверка упала или пропущена — так
  и пишем, с выводом.

## Документы проекта

- `docs/product/PRODUCT.md` — продуктовый документ: сегмент, фазы, решения.
- `docs/product/CABINETS.md` — кабинеты и консоль операций.
- `docs/product/FUNCTIONAL.md` — модули, инварианты, денежный флоу, биллинг.
- `docs/research/` — отчёты исследований, каждый с датой и статусом.

Любое изменение продуктового решения отражается в документе **до** кода.
